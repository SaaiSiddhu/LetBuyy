# Mumbai KYC evidence stack candidate

**Owner:** `services/api-gateway` for upload intent, signed S3 HEAD, review and cleanup; `services/queue-workers` for scan-result polling. **Status:** source candidate only. The owner confirmed on 2026-11-02 that no AWS account is ready. This stack has not been deployed or validated by AWS. The API and worker deliberately allow the India flow only in `ENVIRONMENT=test` until the real-account gate below passes.

`kyc-india-mumbai.cfn.json` defines a private, versioned, SSE-S3 bucket with public access blocked and CORS limited to one exact HTTPS Merchant origin. Deleting or replacing the stack retains the bucket. It defines a GuardDuty Malware Protection plan for `kyc/`, a same-region EventBridge scan-result rule, an encrypted SQS queue, and a dead-letter queue. The scanner role can read and tag only `kyc/*` objects, with a separate exact-object permission for GuardDuty's validation object. The queue policy limits EventBridge sends to this rule and account. GuardDuty tags scanned versions; the reviewer identity may read only a version tagged `NO_THREATS_FOUND`. [AWS documents this tag-based control](https://docs.aws.amazon.com/guardduty/latest/ug/tag-based-access-s3-malware-protection.html) and its additional tagging charge. No replication configuration or public URL is defined. The stack stores no AWS access key or KYC document.

The template defines five distinct IAM users and one STS upload role with narrow permissions for upload, version-specific HEAD, clean-only reviewer GET, version cleanup, and SQS polling. It creates **no access keys, passwords, or managed secrets**. The upload source can assume only the upload role; the Gateway adds an exact-object session policy to each short-lived upload. The HEAD identity may inspect an unscanned object only to bind the exact upload version and checksum; it is not the reviewer identity. A same-region SNS topic emails a required operations mailbox if scan results reach the dead-letter queue, the oldest pending result is at least ten minutes old, or the exact GuardDuty plan reports Warning/Error or a post-scan tag failure. Its topic policy permits only this stack's queue alarms and health rule to publish. The health rule transforms the event into a short message containing only its event type; raw object keys never enter the alert email. The mailbox must confirm its subscription and receive synthetic alarms before real intake. The selected [raw-document retention policy](../../docs/implementation/general-business-wave6-2026-10-30/KYC_RETENTION_DECISION.md) has local, test-only orphan/replacement cleanup, pending expiry, closure cleanup, an overdue-count monitor and an exact-receipt legal-hold candidate with a locally tested Console review/release UI. Final provider-decision deletion, redacted-record expiry and delivered deletion-deadline/hold-review alerts remain open. This stack does not use a blanket S3 expiry rule that might delete a still-referenced version. Provider verification and account-specific legal/security review remain required.

Local source validation is `python3 -m json.tool infrastructure/deployment/kyc-india-mumbai.cfn.json >/dev/null` followed by `node --import tsx --test tests/contracts/kyc-india-mumbai-stack.test.ts`. These check JSON and important static security relationships; they do not replace AWS `validate-template`, change-set review, or a real scan-delivery test.

## Review and apply sequence

1. The owner creates and controls the AWS account. Record its 12-digit ID privately; do not paste credentials into chat or source. Select `ap-south-1` for the stack and verify the intended account with `aws sts get-caller-identity` before any change set. Use different stacks, buckets, origins, principals, and secrets for test/staging and production.
2. Review the template, exact Merchant HTTPS origin, globally unique bucket name, IAM service and app roles, GuardDuty scan/tag costs, retention policy, and CloudFormation change set. The [AWS CLI deploy command](https://docs.aws.amazon.com/cli/latest/reference/cloudformation/deploy.html) supports `--no-execute-changeset` for this review:

   ```sh
   aws cloudformation deploy --region ap-south-1 \
     --template-file infrastructure/deployment/kyc-india-mumbai.cfn.json \
     --stack-name letbuyy-kyc-test \
     --capabilities CAPABILITY_IAM \
     --parameter-overrides BucketName=OWNER_UNIQUE_BUCKET MerchantOrigin=https://OWNER_MERCHANT_HOST ScanRuleName=letbuyy-kyc-test-scan ScanHealthRuleName=letbuyy-kyc-test-health OpsAlertEmail=OWNER_OPS_EMAIL \
     --no-execute-changeset
   ```

   Execute the reviewed change set only through the deployment approval gate. The bucket must be empty of real KYC documents until the rest of this gate is complete.
3. Read back the account, bucket Region, versioning, encryption, public-access block, CORS, bucket policy, and absence of a replication configuration. Wait for versioning propagation before a first write; [AWS recommends 15 minutes](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-s3-bucket.html) after initial enablement. Confirm the GuardDuty plan reports `ACTIVE`, its exact ARN matches the Worker configuration, and it scans an uploaded **synthetic** PDF/JPEG/PNG object in Mumbai. [GuardDuty scans in the bucket's Region](https://docs.aws.amazon.com/guardduty/latest/ug/how-malware-protection-for-s3-gdu-works.html) and sends scan results to the default regional EventBridge bus. A plan in `WARNING` or `ERROR` is not accepted. Confirm the operations mailbox SNS subscription; trigger both queue alarms, a synthetic exact-plan Warning/Error event and a post-scan tag-failure event, then prove an operator receives each redacted alert. [AWS documents these EventBridge event types](https://docs.aws.amazon.com/guardduty/latest/ug/monitor-with-eventbridge-s3-malware-protection.html).
4. Read back the five generated IAM user ARNs and upload role ARN. After separate security review, create credentials for each user through the account's approved secret workflow, store them in managed runtime secrets, and rotate them under a documented schedule. Use different stacks, identities and secrets per environment; do not use root credentials or a shared all-purpose key. Map upload source to `KYC_INDIA_STS_*` and `KYC_INDIA_UPLOAD_ROLE_ARN`, HEAD to `KYC_INDIA_HEAD_*`, reviewer to `KYC_INDIA_REVIEW_*`, cleanup to `KYC_INDIA_CLEANUP_*`, and the worker to `KYC_INDIA_SQS_*`. Prove each identity is denied every other action and bucket, that review fails before the clean tag exists, and that a threat tag never authorizes review.
5. Run a synthetic direct browser and mobile POST through the real S3 origin. Confirm a version-specific 201 and checksum, the API's authenticated HEAD/readback of that exact version, a GuardDuty clean and threat result arriving through the actual SQS queue, duplicate/early/wrong-version rejection, a Console reasoned clean-only review, and replacement/orphan version cleanup. Record the exact account, bucket, plan, queue, site, receipt and object version in restricted evidence, without document bytes, access keys, or signed URLs. Alarm and investigate skipped/failed scans, plan degradation, queue age, and dead-letter messages. Prove the selected retention policy's deletion deadlines and legal-hold exception before a real document is accepted.
6. Only after the AWS, provider, privacy, security, finance, and hosted gates pass should an explicit production configuration change remove the code's `ENVIRONMENT=test` restriction. A bucket and scan plan alone cannot make a merchant verified or enable payouts.
