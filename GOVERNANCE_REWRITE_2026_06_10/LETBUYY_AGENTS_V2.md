# 1. ARCHITECTURE RULES (`ARCH`)

> The single canonical architecture (memorize this): **one modular monolith (`api-gateway`) + four satellites (`queue-workers`, `mobile-bff`, `identity-platform`, `webhook-service`) over one RLS+GUC Postgres on Cloudflare (ap-south) + Vercel, one region** — canonical double-entry ledger as the sole money truth, `identity-platform` as sole asymmetric token issuer, server-authoritative Liquid-first commerce with a hosted `checkout.letbuyy.com` origin — every Shopify-scale capability frozen as an empty seam. (ADR-004; Constitution §2.)

### 1.1 The canonical runtime topology (`ARCH-TOPO`)

- **ARCH-R1 — MUST** treat the following **8 runtimes** as the entire canonical active topology. This is the V1 8-runtime set, **NOT** the rejected 9-app AGENTS set.

  **The 8 canonical runtimes (the only deployable topology):**

  | # | Runtime | Kind | Role |
  |---|---|---|---|
  | 1 | `services/api-gateway` | Worker (modular monolith) | The commerce backend — auth, products, cart/checkout, orders, payments, inventory, discounts, GST, shipping, settlement, customers, themes, WhatsApp, notifications, billing, analytics-read |
  | 2 | `services/queue-workers` | Worker (satellite) | Outbox relay, WhatsApp/email send, settlement & reconciliation jobs, abandoned-cart, rollups, stale-reservation sweeper |
  | 3 | `services/mobile-bff` | Worker (satellite) | A real composite/fan-in BFF (`/v1/dashboard`) for the Flutter app |
  | 4 | `services/identity-platform` *(app root: `apps/identity-platform`)* | Issuer satellite | The **sole** asymmetric token issuer for all three realms |
  | 5 | `services/webhook-service` | Worker (satellite) | Outbound webhooks (HMAC + dedupe) and provider callback ingress |
  | 6 | `apps/storefront-runtime` | Vercel/Next | The one buyer runtime; hosts the Liquid renderer + the hosted `checkout.letbuyy.com` origin |
  | 7 | `apps/merchant-control-plane` | Vercel/Next | The merchant web OS (operator-first IA) |
  | 8 | `apps/marketing-site` | Vercel/Next | Public marketing/pricing (no auth pages) |

  *Plus the supporting, non-extractable surfaces that ride this topology:* `apps/mobile/merchant-app` (Flutter), and **one** thin ops console (`apps/platform-console` — see `ARCH-R10`). The Next read/admin apps are thin composition layers over the monolith; they are not a "service fleet."

- **ARCH-R2 — MUST NOT** add, deploy, or wire any runtime not in `ARCH-R1`. Adding a new runtime root requires a Constitution amendment + ARB approval + DOC 03/04 updates **before** source is created. (Enforced by `runtime-manifest-validator` retargeted to the V1 8-runtime list; `[validator-gap]` for the deploy↔V1-topology contract — ADR-002.)
- **ARCH-R3 — MUST NOT** extract any domain (payments, checkout, identity, search, media, notifications, analytics) into its own microservice. Capabilities live **in the monolith** (or `queue-workers` for async). Microservice extraction is reversible only at a **named, measured scale trigger** under human approval (ADR-004). Modular boundaries *inside* the monolith preserve the option; do not exercise it.

### 1.3 Forbidden rejected-architecture wiring (`ARCH-FORBID`)

# 3. WINNER-SELECTION RULES (`WIN`)

> The single most consequential class of rule for drift prevention. When two implementations of one domain exist, the agent does **not** pick the busier or more-complete one — it picks the **strategic winner** and refuses to build a third.

### 3.1 The decision rule (`WIN-RULE`)

- **WIN-R1 — The Strategic Winner is the implementation that should still exist at 10,000 India merchants — NOT the oldest, the most complete, or the easiest to keep.** LetBuyy has **zero production merchants and zero legacy burden**, so it moves directly to the intended architecture and preserves nothing for its own sake. (Constitution §0.2; ADR preamble.)
- **WIN-R2 — MUST** consult `DOC 03` (`LETBUYY_CANONICAL_SYSTEMS.md`, the winner registry) before choosing which of two systems to edit, extend, or call. The registry names the one true system per domain. If `DOC 03` is silent on a pair, **escalate** — do not pick by completeness.
- **WIN-R3 — The decision rule crowns the *less complete* thing wherever the less complete thing is the one that scales or supports the ecosystem.** The canonical winners (do not re-litigate — they are decided):
  - **Money:** the canonical double-entry ledger (mig 139–161) over the busier legacy capture path.
  - **Theme:** **Liquid / portable-theme (OS-2.0)** over the more-complete React section renderer.
  - **Identity:** `identity-platform` over the more-load-bearing gateway `routes/auth.ts`.
  - **Tenancy:** RLS+FORCE+GUC over the app-only tenant guard (the guard stays as an outer layer, not the sole control).

### 3.2 Never build a parallel second system (`WIN-PARALLEL`)

- **WIN-R4 — MUST NOT** build a **parallel second system** for any domain that already has a canonical winner. "Two parallel systems" (legacy vs canonical ledger, React vs Liquid, legacy vs V1 auth, dual draft systems) is the program's #1 anti-pattern and the maintenance tax this rewrite exists to end. (FORENSIC_MASTER; `ANTI-R1`.)
- **WIN-R5 — If you discover two systems for one domain, MUST escalate to collapse-not-coexist.** The rule is *one of everything*. Do not "harmonize" or "bridge indefinitely"; name the winner (per `DOC 03`), make the loser a `TRANSITIONAL`/`LEGACY` bridge, and schedule its gated deletion (`DEL`). MUST NOT leave both live as a permanent design.
- **WIN-R6 — MAY** complete an unfinished canonical winner (wire it, finish its tests, fill its gaps). This is the encouraged work. MUST NOT, in the name of "completeness," resurrect or extend a `LEGACY`/`DEAD` loser.
- **WIN-R7 — A stub/mock that is the canonical design (e.g. `mobile-bff`, the consent ledger, the hosted checkout origin) MUST be *completed*, never replaced by a parallel re-implementation in a different runtime.** Completing the named winner is correct; building a second one beside it is `WIN-R4` drift.

# 4. MIGRATION RULES (`MIG`)

- **MIG-R1 — Clean replacement over backward-compat.** There are **zero real merchants**, so MUST move directly to the canonical schema and MUST NOT preserve a legacy shape for its own sake. (Constitution; ADR-024.)
- **MIG-R2 — Sequential numbering.** New migrations MUST be numbered sequentially from the **current max (161)** — i.e. the next migration is `162`. MUST NOT reuse or skip prefixes; MUST fix the existing duplicate prefix (129) and MUST NOT introduce new duplicates. (`migration-history-validator`; `[validator-gap]` dup-prefix check.)
- **MIG-R3 — Every migration MUST ship a forward AND a paired rollback (DOWN).** A migration without a DOWN is a defect. The three known unpaired migrations (138/140/157) MUST gain rollbacks; a **rollback-pairing validator gates merge for any migration ≥ 138** (`[validator-gap]` — ADR-002 ADD bucket).
- **MIG-R4 — Data cutovers MUST follow expand → backfill → verify → contract.** Add the new column/shape (expand), backfill with a **zero-loss** job, **verify** parity (per-row equality / `variance=0`), then drop the old column (contract). MUST NOT drop the old shape before parity is proven. (ADR-010/013.)
- **MIG-R5 — MUST NOT** make a migration depend on a generated application artifact, and MUST NOT couple a money/representation cutover to a beta-blocking wave — the bigint cutover is Wave 5, after the Wave-1 correctness wiring (ADR-013).
- **MIG-R6 — Money/audit tables MUST be append-only at the schema level** — enforced by **trigger AND `REVOKE UPDATE/DELETE`** + RESTRICT FKs, never trigger-only. (Cross-listed `PAY-R6`; ADR-010.)

# 5. DELETION RULES (`DEL`)

> Constitutional deletion law (ADR-024). Nothing load-bearing is deleted until a green validation gate proves it safe. The deploy meta-blocker (`DEPLOY-R1`) is the keystone — no deletion that requires a deploy can be validated until `main` is current.

- **DEL-R1 — MUST NOT delete anything until its deletion-validation is green.** A deletion that is not deletion-validation-green is a **regression, not a cleanup.** (Testing plan RULE 1.)
- **DEL-R2 — Two deletion classes, two disciplines:**
  - **`SAFE_DELETE`** (zero production importers, no value) — delete after **V-IMPORT** (zero non-self/non-validator importers, by `grep @letbuyy/<pkg> apps services packages`) + **V-BUILD** (`pnpm turbo build` / `flutter analyze` green) + **V-TEST** + **V-GOV** (governance green *after* the asserting validator is retargeted). Goes first and cheap.
  - **`DELETE_AFTER_MIGRATION`** (wired into a live path today) — delete **only once** the Strategic Winner is **live and serving (V-SMOKE)** AND the legacy importer count returns to **zero**. For money paths, also a **reconciliation-harness zero-drift proof**; for renderers, **parity + security + perf green per-section**; for tables, **`pg_stat_user_tables` zero recent writes**.
- **DEL-R3 — The validator-liveness ordering (the single most error-prone step):** when deleting a `DEAD` package that a validator asserts, MUST **retarget/remove the asserting validator FIRST (or in the same change), then delete the package** — deleting the package before the validator fails CI. `V-GOV` runs **after** the paired validator edit, never before. (ADR-002; Testing plan §9.)
- **DEL-R4 — MUST** perform deletions on a branch, behind the deploy meta-blocker fix, with paired DOWN migrations / archived DDL so every deletion is reversible until proven safe (`git revert` must restore a building tree). (ADR-024.)
- **DEL-R5 — MUST NOT** blind-drop a table that "looks dead." Some dead-looking tables have **RPC/ops-script writers not visible in code** (~37 product-dead tables, 6 superseded theme tables). MUST confirm with `pg_stat_user_tables` write counts before any DROP. (UNVERIFIED in the audit — treat as a live check.)
- **DEL-R6 — MUST** reference DOC 04 (`LETBUYY_LEGACY_ELIMINATION_MASTER_PLAN.md`) and the `LEGACY_ERADICATION_REGISTER.md` (LEG-001…078) / `SAFE_DELETION_PLAN.md` (DEL-0…078) for the per-artifact gate and wave. MUST NOT invent a deletion order that contradicts the wave model.

- **NEVER-R2 — MUST NOT build:** a **money-custody** payout/disbursement engine (the `razorpayx` self-custody rail is DEAD — LetBuyy never holds funds) · a cross-merchant wallet / Shop-Pay-style vault.
- **NEVER-R3 — MUST NOT build (as live capability):** a 3rd-party app marketplace · checkout extensions / app-functions / Wasm runtime in the live path · theme app-blocks for third-party authors. (Reopen at ≈5k merchants + inbound developers; keep the OAuth2/PKCE + `appBlockSlot` seams.)

- **NEVER-R5 — MUST NOT introduce any GMV/transaction fee.** The transaction fee is **0%, permanent** (cross-listed `PAY-R3`).
- **NEVER-R6 — MUST NOT fill any of the six reserved services** (`ARCH-R4`).
- **NEVER-R7 — The one-line test (apply it before building anything new):** *if it imitates Shopify's end-state and no beta merchant would notice its absence, it is forbidden until a named trigger fires* (`ENV-R3`). When unsure whether a capability is in-envelope, **escalate** (`PRIME-R1`).

> The two hard rules (Testing plan §0): **no system is deleted until its deletion-validation is green** (`DEL-R1`); **no wave exits until its validation gate is green.** Validators are *structural lints*, NOT behavioral tests — real coverage must be **built**, not asserted by file presence.

### 7.1 The 9-class taxonomy (`TEST-CLASS`)

- **TEST-R1 — Every migration/winner MUST be tested across the 9 classes** (class-appropriate subset where noted): **Unit · Integration · Contract · E2E · Security · Performance · Regression · Rollback Validation · Deletion Validation.**
- **TEST-R2 — MUST** apply the **rigor escalation** — the heaviest (FULL 9-class) suites land on **Money, Tenancy, Auth, Checkout, and Theme-Liquid**. The reconciliation harness is the **money-cluster deploy gate AND the deletion gate for every legacy money path.**

# 8. SECURITY RULES (`SEC`)

> Fail-closed everything. The forensic audit found **9 S0 vulnerabilities shipping live** behind a green gate; these rules close them and forbid their re-introduction.

### 8.1 Posture (`SEC-POSTURE`)

- **SEC-R1 — Everything fails closed.** A missing/unset tenant GUC ⇒ **zero rows.** A missing consent record ⇒ **hard-stop the send** (never open it). A misconfigured RLS table ⇒ surfaces immediately (never silently leaks). An omitted tenant gate ⇒ **deny** (default-deny middleware). (ADR-007/008.)
- **SEC-R2 — MUST NOT** commit any secret to the repo (no `AUTH_SECRET`, provider keys, KMS material, DNS credentials, Wrangler/MCP auth files). Server secrets live in Vercel/Cloudflare/CI secret stores or operator shells. `NEXT_PUBLIC_*` MUST never contain secrets. Env files are local-only and untracked.
- **SEC-R3 — MUST NOT** expose a Supabase `service_role` (or any privileged) key to a client component. Service-role references stay server/worker-only.
- **SEC-R4 — MUST NOT** store auth tokens in `localStorage`. Local storage is for non-secret UI preferences / preview-only state only. Cookies are HTTP-only, Secure in production, SameSite=Strict unless a documented cross-site redirect exception exists.
- **SEC-R5 — Webhook side effects MUST verify the provider signature, enforce a timestamp/replay window, and record an idempotency key/event id BEFORE any mutation.** (Cross-listed `PAY-R8`.)

### 8.2 The specific S0 prohibitions (`SEC-S0`)

- **SEC-R6 — MUST NOT** create or retain any RLS policy that is `USING(true)` to **PUBLIC** (or otherwise grants anon/`authenticated` read/write of tenant data). The six baseline PUBLIC policies (orders, customers/PII, billing, products, sites, subscriptions) are **DEAD (S0)** and re-scoped to `TO service_role` + owner + GUC in migration `162`; `REVOKE INSERT/UPDATE/DELETE FROM anon, authenticated` is mandatory. (ISSUE-004…008; ADR-009; CI policy-lint forbids it.)
- **SEC-R7 — MUST NOT** sign tokens with a **shared symmetric secret** across trust domains. The shared-`AUTH_SECRET` HS256 (where the verification key *is* the forgery key across seven domains) is DEAD; tokens are **asymmetric, single-signer** (cross-listed `IDN-R2`). MUST NOT use `AUTH_SECRET` as a fallback for any other secret (the webhook internal-secret `|| AUTH_SECRET` fallback is DEAD — use a dedicated `INTERNAL_API_SECRET`). (ISSUE-027; PAY-023; ADR-005.)
- **SEC-R8 — MUST NOT** create or retain an **anon-writable privilege table** (e.g. the `super_admin_allowlist` anon-insert self-grant). Privilege tables are `TO service_role` + an audited migration-write path + an INSERT audit trigger. (ISSUE-003; ADR-006.)
- **SEC-R9 — The gateway MUST NOT connect as blanket `service_role` for tenant data.** Tenant data runs over a pooled transactional connection under a non-`BYPASSRLS` `app_tenant` role (`withTenantTx(siteId, fn)`); `service_role` is a narrow, audited break-glass hatch (`withServiceRole(reason, fn)`). (ISSUE-009; ADR-008; cross-listed `SEC-R12`.)
- **SEC-R10 — MUST NOT** trust client-submitted role/identity. Role comes only from `app_metadata`/DB, never `user_metadata`. The `/api/auth/switch` path MUST require a valid session + membership (the fix is committed + deployed in Wave 0). (ISSUE-001; AUTH-004; ADR-006.)
- **SEC-R11 — MUST** render output through an allowlist/DOMPurify sanitizer (not a regex), and MUST close the storefront stored-XSS pair and the webhook SSRF before any buyer traffic. (ISSUE-016/017/020.)

# 9. PAYMENT RULES (`PAY`)

> Money is one append-only double-entry ledger as the sole truth, `bigint` paise, never-custody PA-split, 0% fee, real crypto step-up. (ADR-010/011/012/013; Constitution §5/§6.)

- **PAY-R1 — The canonical append-only double-entry ledger (8 accounts, mig 139–161) is the SINGLE money source of truth.** Balance is **always derived** (`ledger_account_balance_minor`), **never** a mutable column. MUST NOT treat any mutable-balance row (wallet/gift-card/store-credit/AI-credit) as money truth — those become read-only projections / ledger tenders. (Mutable-balance-as-truth is a root-cause P0 class — `ANTI-R4`.)
- **PAY-R2 — Every capture / refund / COD / tender posting MUST go through the ledger, idempotently** (capture → debit `pa_clearing` / credit `merchant_payable`; refund → debit `merchant_payable` / credit `refund_clearing`; COD → `cod_receivable` at confirm, relieved at remittance with **signed** breaks). MUST NOT add a money path that captures without posting (the legacy `confirm_order_payment_with_ledger` posts **zero** ledger entries despite its name — it becomes an adapter, then LEGACY). (ISSUE-010/011/018/019.)
- **PAY-R3 — 0% transaction fee, permanent.** MUST set `commission_bps = 0`; the 3% GMV rake default + the 18% GST-on-fee are **DEAD**. A `commission_bps=0` ratchet validator prevents regression. Monetization is subscription + adjacencies, never the sale. MUST NOT make the fee per-merchant-configurable. (ISSUE-015; ADR-012.)
- **PAY-R4 — Never custody.** Money-out is a **PA-split instruction + statement-mirror + reconciliation** through a licensed PA (Razorpay Route / Cashfree); money-in flows to the **merchant's own Razorpay** (merchant = merchant-of-record). The `razorpayx` self-custody rail is **DEAD**; MUST NOT re-enable it and MUST NOT stamp `no_custody:true` on a self-custody path — derive `no_custody` from the rail. (ISSUE-014; ADR-011.)
- **PAY-R5 — `bigint` minor units (paise) on every money path.** MUST NOT introduce int32 paise (overflows at ₹2.14cr), numeric-rupee, numeric(16,4), or float for money. The mixed representations are LEGACY → expand/contract cutover (Wave 5). (ISSUE-025; ADR-013.)
- **PAY-R6 — Append-only enforced by trigger AND `REVOKE UPDATE/DELETE`** + RESTRICT FKs on ledger/audit (not trigger-only). One **writer module** (settlement); the `writer_module` CHECK constraint (mig 139) MUST hold. A wrong posting is corrected by a **reversing entry, never a mutation.** (Cross-listed `MIG-R6`.)
- **PAY-R7 — The second factor on refund/payout MUST be real cryptography** (HMAC / stored-challenge), never a string-length check. The forgeable step-up is DEAD. (ISSUE-012; ADR-011.)
- **PAY-R8 — MUST** recompute totals server-side, verify provider signatures, and require idempotency on every payment/mutation endpoint (cross-listed `CODE-R6`, `SEC-R5`). MUST NOT trust client totals or provider names.
- **PAY-R9 — Reconcile to zero-break-or-explained-suspense.** MUST NOT auto-plug a reconciliation difference; surface drift via `recon_breaks` (signed). The reconciliation honesty gate (`money_ledger_site_reconciliations`, no auto-plug) is canonical. (ADR-010.)
- **PAY-R10 — Provider-mode honesty is mandatory:** a mock/sandbox provider MUST NOT read as `success`. Every money/fulfillment surface renders a truthful `mock/sandbox/live` badge (cross-listed `UI-R6`, `AGENT-R12`). (ADR-020.)

# 10. IDENTITY RULES (`IDN`)

> `identity-platform` is the sole issuer; services verify-only; no second auth system; realm separation; validated claims → GUC. (ADR-005/006/007.)

- **IDN-R1 — `identity-platform` is the SOLE issuer** of all identity for all three realms (merchant/staff, buyer/customer, platform-operator) — OTP, login, sessions, cookies, refresh rotation, the DPDP consent ledger, MFA, passkeys, the OIDC provider. MUST NOT mint sessions/tokens anywhere else. The four parallel auth implementations (gateway `routes/auth.ts`, the gateway `identity-foundation` shadow stack, legacy Supabase `/auth/*`, the per-app session libs) collapse into one; gateway/services become **verify-only**. (ADR-005; `WIN-R4`.)
- **IDN-R2 — Tokens are asymmetric, single-signer** (EdDSA/Ed25519; ES256 fallback) via a real KMS; **every other runtime is verify-only** with the published public key, per-audience (`aud`) claims. MUST NOT sign with a shared symmetric secret (cross-listed `SEC-R7`). The token cutover is **dual-verify**: revert is a verifier-pin change, never an issuer revert; a rollback drill is mandatory before dropping HS256, gated on **zero legacy-HS256 verifications** telemetry. (ADR-005.)
- **IDN-R3 — MUST NOT build a second auth system.** If you find a parallel auth path, it is a `LEGACY`/`DEAD` loser to collapse, not a thing to complete or harmonize (`WIN-R5`). MUST NOT "fix" the identity-foundation shadow stack — it is `SAFE_DELETE` after `identity-platform` serves verify-only.
- **IDN-R4 — Realm separation:** storefront/buyer auth MUST NOT grant merchant/admin privileges; console/operator auth enforces email allowlists, TOTP/2FA, and audit logging. (Cross-listed `ARCH-R18`.)
- **IDN-R5 — The tenant GUC value MUST come from a *validated* claim** (couples to `IDN-R2` and `SEC-R9`). MUST NOT set the tenant GUC from a raw request param (the GUC-from-param ledger primitive is DEAD — derive tenant from the authenticated principal in-RPC). (ISSUE-013; ADR-008.)
- **IDN-R6 — The DPDP consent ledger is canonical, append-only, and fail-closed** — a missing consent record hard-stops the matching send (never opens it); it gates WhatsApp/marketing/analytics. OIDC and passkeys are **canonical-but-DEFERRED** — until real, OIDC serves **404, never a placeholder `MOCK_JWKS`** (the literal is removed in the token cutover). (ADR-007.)

# 16. AGENT BEHAVIOR RULES (`AGENT`)

> The operational contract for what an agent MAY do, may NEVER do, and how it handles mocks, human-required integrations, frozen architecture, legacy removal, and escalation. This section binds all the above into agent behavior.

### 16.1 What an agent MAY do (`AGENT-MAY`)

- **AGENT-R1 — MAY** make scoped edits **within a canonical winner** (fix a bug, add a field, complete a flow), using service-layer logic, shared types, Zod validation, and existing local patterns. This is the encouraged default.
- **AGENT-R2 — MAY** **complete an unfinished canonical winner** (wire the ledger capture, set the GUC, schedule the sweeper, build the BFF composite, build the consent ledger, ship the hosted checkout origin) — these are the high-value tasks (`WIN-R6`, PRIME-R3).
- **AGENT-R3 — MAY delete validated legacy** once its deletion-validation gate is green (`DEL`), on a branch, behind the deploy meta-blocker, with paired rollback.
- **AGENT-R4 — MAY** add/retarget a validator to enforce a Constitution rule (e.g. the `commission_bps=0` ratchet, the rollback-pairing check, the topology anti-fabrication check).

### 16.2 What an agent may NEVER do (`AGENT-NEVER`)

- **AGENT-R5 — MUST NEVER build a parallel second system** for a domain with a canonical winner (`WIN-R4`).
- **AGENT-R6 — MUST NEVER wire rejected architecture** (CQRS/saga/event-bus/projection/multi-region/Wasm-runtime; the dead package cluster) — even to "complete" or "re-enable" it (`ARCH-R7/R8/R9`).
- **AGENT-R7 — MUST NEVER expand scope past the 10k envelope** or build a `NEVER`-list capability without a named trigger + human approval (`ENV`, `NEVER`).
- **AGENT-R8 — MUST NEVER promote a generated/scan artifact to authority** or hand-author a doc that re-declares drift as law (`DOC-R1`).
- **AGENT-R9 — MUST NEVER mark a stub/mock as success** or remove/weaken an honesty badge (`AGENT-R12`, `PAY-R10`).
- **AGENT-R10 — MUST NEVER delete without a green validation gate** (`DEL-R1`), and MUST NEVER custody money (`PAY-R4`, `NEVER-R2`).

### 16.3 Human-required integrations & mocks (`AGENT-HUMAN`)

- **AGENT-R11 — Human-required integrations are mock-by-default, badged, and marked.** When a real integration needs human action (live PA/Razorpay/Route keys, KYC, WhatsApp BSP, ESP, a KMS key), the agent MUST: (a) implement against a **mock/sandbox adapter** by default; (b) render the **honesty badge** (`mock/sandbox`); (c) mark the seam **`[HUMAN-REQUIRED]`** in code/docs; (d) **never fake success** — a mock MUST NOT report `live`/`success`. MUST NOT block the whole feature on the human gate — build behind a flag with the mock as the fallback. (Constitution §1 P4; ADR-011/015/020.)
- **AGENT-R12 — Mocks are honest and isolated.** A mock provider MUST be clearly a mock (badge + flag), MUST NOT leak into a path that reports a real money/fulfillment outcome, and MUST be replaced only by the **canonical** real adapter (never by a parallel second adapter — `WIN-R7`).

### 16.4 Frozen architecture — leave the seam (`AGENT-FROZEN`)

- **AGENT-R13 — When the architecture is frozen at a seam, MUST leave the seam empty and MUST NOT fill it.** The Wasm checkout runtime, headless Hydrogen, app-marketplace, the six reserved services, theme app-blocks for third parties, partitioning — all are **documented seams**, not builds. The agent's job at a frozen seam is to *preserve the interface*, not to implement behind it (`ARCH-R9`, `NEVER`, ADR-016/018/019/022/023).

### 16.5 Legacy removal — the gated process (`AGENT-LEGACY`)

- **AGENT-R14 — Removing legacy MUST follow the gated process:** name the winner (DOC 03) → confirm the winner is live/serving (`V-SMOKE`) for `DELETE_AFTER_MIGRATION`, or zero-importer for `SAFE_DELETE` → retarget the asserting validator **first** (`DEL-R3`) → run V-IMPORT/V-BUILD/V-TEST/V-GOV (+ zero-drift for money, parity for renderers, `pg_stat` for tables) → delete on a branch with a paired rollback. MUST NOT shortcut this for a "small" or "obviously dead" item (`DEL-R5`).

### 16.6 Escalation triggers (`AGENT-ESCALATE`)

- **AGENT-R15 — MUST escalate to a human ARB decision (do not improvise) when any of these fire:**
  1. Two implementations of one domain exist and DOC 03 does not name the winner (`WIN-R2`).
  2. A change would add a runtime, fill a reserved service, or wire a rejected package (`ARCH-R2/R7`).
  3. A change would expand past the 10k envelope or touch a `NEVER`-list capability (`ENV`, `NEVER`).
  4. A rule here appears to conflict with the Constitution (DOC 01) — the Constitution wins; surface the defect (`PRIME-R1`).
  5. A deletion's validation gate cannot be made green, or a "dead" table has unknown live writers (`DEL-R5`).
  6. Any item still flagged **UNVERIFIED** in the evidence base must be resolved as a *decision* or recorded as a genuine live/vendor probe, not assumed (`ARCH-R10`).
  7. A money/identity/tenancy change would weaken a fail-closed default or an S0 fix (`SEC-S0`, `PAY`, `IDN`).
