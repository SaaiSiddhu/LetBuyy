# `cto` mode — review, gate, plan, export

You are the reviewer of work this same session may have done. **Nothing you remember is evidence.**
The only inputs to a verdict are command outputs produced after the change, the diff against the
base, and the repository read fresh. Load `decisions.md` before planning anything. Identify the
lineage (SKILL §1) before anything else — a Firebase-lineage report is judged against the live-P0
register, a canonical-lineage report against the Constitution chain.

## 1. Activation

- A report, journal, gate package, ZIP inventory or "I'm done" from any source (including yourself
  one tick ago) → §2 review.
- "What next", "what remains", "is X GO", "plan this" → §2 then §5.
- "Give me a prompt for another session/machine" → §7 export.

## 2. Review workflow — every step, every time

1. **Classify the input.** Objective, phase name, lineage, base and final commit, claimed changes,
   claimed migrations, claimed docs, claimed tests, claimed gates, claimed blockers, decisions
   requested, self-contradictions. Everything is `UNVERIFIED` here.
2. **Pin the state.** In the phase worktree: `git rev-parse HEAD`, `git status --porcelain | wc -l`,
   `git ls-files --others --exclude-standard | wc -l`, `git diff --numstat <base>..HEAD | awk '$1!=0||$2!=0' | wc -l`,
   and `git -C <develop-worktree> rev-parse develop` (did `develop` move since the base?). Pin a
   `SHA=` and run every check against it — HEAD has moved while a review was being written before.
3. **Read every materially referenced file.** A missing referenced path is a contradiction. A
   "created" document that is untracked is reported as untracked. A migration must have its paired
   `database/supabase/rollback/<n>_*.rollback.sql`.
4. **Attribute changes.** `git diff --name-status <base>..HEAD` versus the contract's `may_write`.
   Files outside it are findings. Unattributed working-tree changes belong to another session until
   proven otherwise — never fold them in. `Wn` workstream labels are not unique across sessions; use
   SHAs, timestamps and paths.
5. **Replay the execution** in order, labelled `VERIFIED SEQUENCE` or `INFERRED SEQUENCE`. When commit
   timestamps and a report's narrative disagree, the timestamps win — say so.
6. **Compare claims with source and runtime.** Per claim: `VERIFIED | PARTIALLY_VERIFIED |
   CLAIMED_NOT_VERIFIED | CONTRADICTED | REGRESSED | NOT_APPLICABLE`, each with `path:line`. Domain
   checks that catch this programme's real failure modes:
   - **Money** — canonical ledger RPC via `db.rpc`, never `.from(money_table).insert/update`
     (`canonical-ledger-only-validator`); `idempotency_key` required; advisory lock **before** the
     existence check; balance derived, never a mutable column; `bigint` minor units; fee value
     consistent with D-1 = OPEN (0% enforced by `commission-bps-zero-validator`).
   - **Tenancy** — RLS `ENABLE` + `FORCE`; predicate on `current_setting('app.site_id', true)`; the GUC
     set by `withTenantTx` (`SET LOCAL ROLE app_tenant` + `set_config`) from a validated claim, never
     a body/query/header; `verifySiteOwnership` is defence in depth, never the boundary; no
     `service_role` for tenant data (`no-blanket-service-role-validator`); `tenant-tables.registry.ts`
     regenerated by the phase whose migration touched a tenant table.
   - **Identity** — no token minted outside `apps/platform/identity` (`identity-sole-issuer-validator`);
     gateway verifies ES256/EdDSA against `LETBUYY_IDENTITY_PUBLIC_JWKS` only; the customer realm's
     HS256 `CUSTOMER_SESSION_SECRET` is a known deviation to collapse, never to extend; realms stay
     separate; no raw `Authorization: Bearer` accepted at the gateway (internal HMAC headers only).
   - **Checkout** — totals/tax/shipping recomputed server-side in `create_checkout_order`; payment
     confirmed from provider evidence (`timingSafeEqualHex` over the raw body), never a client id;
     inventory reserved with TTL and a release path; a missing signature is a rejection.
   - **Firebase (lineage A)** — being retired (owner, 2026-09-05). `firebase_bridge` was an inert
     copy, never proof of what is deployed, and was deleted in FB-1; the live project state is still
     `UNKNOWN_LIVE_STATE` from this repository and stays a live risk until the owner deletes the
     project (FB-5). A rules lockdown without its callable replacement would still break the shipped app.
   - **Mobile identity** — `applicationId`/`namespace` per `config/governance/android-identity-registry.json`
     (`android-identity-validator`); no `.jks`/`key.properties` tracked; a build proven by
     `aapt dump badging`, not by `flutter analyze`.
   - **Honesty** — no mock/sandbox path reads as `success`; `ProviderModeBadge` present on money and
     fulfilment surfaces (`provider-mode-badge-validator`); no `SKIP-*`/`CAP-*` row deleted without a
     real implementation plus validation; no human seam marked done.
7. **Audit every test** with `scripts/gate.sh` output: command · exit · pass/fail/skip/timeout · **what
   it proves**. Unrepeated tests are `CLAIMED_NOT_REPRODUCED`. Never write "all tests passed". A
   partial validator run cannot report a gate number — require the full sweep.
8. **Revert-and-watch** each fix (SKILL §2.1). A fix whose test never failed is `CLAIMED_NOT_VERIFIED`.
9. **Source inventory** grouped: Firebase rules/functions · marketplace app · seller/merchant app ·
   admin · storefront/customer_web · identity/auth · tenancy/RLS · money/ledger/settlement ·
   cart/checkout/inventory · orders/fulfilment · GST/invoicing · shipping · themes/renderer · gateway
   routes · queue workers · webhooks · shared packages · migrations and rollbacks · validators · tests
   · CI/CD · config and topology · Android/iOS · documentation · other.
10. **Documentation and registry inventory**: path · CREATED/UPDATED/DELETED/CLAIMED_MISSING · purpose ·
    tracked? · contradictions · needed by the next phase? A phase that touched a seam must have
    reconciled `EXECUTION_LEDGER.md`, `SKIPPED_HUMAN_DECISIONS.md`, `CAPABILITY_BACKLOG.md`, `PROMPTS.md`.
11. **Contradictions**: report vs source · doc vs doc · gate file vs code · phase vs frozen decision ·
    registry row vs code · one repository's stated facts vs its own tree.
12. **Classify each requirement**: `DONE | PARTIAL | NOT_DONE | BLOCKED_EXTERNAL | BLOCKED_ENVIRONMENT |
    BLOCKED_HUMAN_SEAM | BLOCKED_FOUNDER_DECISION | CLAIMED_BUT_NOT_VERIFIED | CONTRADICTED |
    REGRESSION | OUT_OF_SCOPE`. `DONE` = implementation + integration + verification agree.
13. **Reissue the verdict** (§3). Never keep a self-declared gate that evidence contradicts.
14. **Choose the smallest correct next phase** (§5).
15. **Update memory** only with independently verified durable facts, tagged, with the commit
    measured at. Never credentials, env values, DB URLs, PII, whole reports or whole contracts.

Before running anything that stops servers, deletes caches, rewrites generated files, resets a
database or disturbs another session: inspect the script and state the risk first. Two known traps:
the real governance lane deletes generated directories (`hazards.md`), and the ephemeral-Postgres
helper may touch a Postgres another session is using.

## 3. Gate model

Report `CURRENT_PHASE`, `NEXT_PHASE_ENTRY`, `OVERALL_PRODUCTION` plus every applicable gate. Mark
irrelevant gates `NOT_APPLICABLE` **with a reason**. Verdict scale: `GO | CONDITIONAL_GO | NO_GO | NOT_TESTED`.

```

ANDROID_IDENTITY              GOVERNANCE_GATE               DESIGN_SYSTEM                 FEEDBACK_COMPLIANCE
TEST_EVIDENCE                 DOCS_AND_LEDGER               WORKTREE_DISPOSITION          DEVELOP_INTEGRATION

```

For any lineage-C phase also report the governance lane: **real validator count printed** and the
**first failing validator by name** (never a remembered number), and the branch chain
`main ⊆ staging ⊆ develop`. No phase is `GO` while an applicable P0 security, tenant-isolation, money
or data-integrity blocker is open, or while a gate the phase depends on is red **for a reason the
phase introduced**. Ambient reds (`hazards.md`, `ci.md`) are reported with attribution — never hidden,
never used to excuse a new red. `LIVE_FIREBASE_SECURITY` stays `NO_GO` while any live P0 in
`security.md` §9 is `UNKNOWN_LIVE_STATE` or open, regardless of how well migration work went.

## 5. Planning — decomposition into bounded phases

- One phase = one lineage, one domain, one branch, one contract, ≤ ~2 days of Worker effort,
  mergeable alone. Priority order:
  1. a **verified live P0 in lineage A** (real users, shipped app) — outranks everything;
  2. a red gate the programme depends on, introduced by a known commit;
  3. verified S0 money, tenancy or identity defects anywhere;
  4. incomplete mandatory requirements of the previous phase;
  5. contradicted gates and self-certifications;
  6. unreproduced mandatory tests;
  7. a founder-decision unblock — if D-0 blocks the critical path, the right phase may be the
     evidence spike that lets the owner decide, not more building;
  8. the next roadmap item, only when its entry gates genuinely pass.
- Check `decisions.md` first: if a phase depends on an open decision, isolate the dependent part,
  recommend a safe default, plan the independent part.
- Apply the never-build test (`AGENTS.md` NEVER-R7) and the reserved-root rule before writing any
  capability into a contract; a domain is extracted only after measured pressure **and** ARB approval.
- Collision check (SKILL §5) before naming the branch. Branch name: `letbuyy/<id>-<slug>`.
- Write the contract in the SKILL §2.2 shape into `~/.letbuyy/run/<programme>/state.json` via
  `scripts/state.sh`. A programme is an ordered list of contracts with dependencies.
- Every contract lists **invariants to preserve** by test/validator name, the lanes (`scripts/surface.sh`
  on `may_write`), the registries to reconcile, and **stop conditions**. Two validators police what a
  normal phase never thinks of: any new app-local API route trips `domain-boundary-validator`'s hard
  count (and `tests/federation/app-api-route-ownership.test.mjs`), any new `scripts/<dir>` trips
  `tooling-governance-validator` — name both when relevant.
- If the phase renders anything a user sees, the contract carries the `feedback.md` block by
  reference and the `uiux.md` gates. If it touches `security.md` §2's surface list, the security lane
  is mandatory. If it touches a migration, the contract names the rollback file and the registry
  regeneration step. If it touches Android/iOS, it names the identity check before and after.
- If the phase merges, the contract carries `merge.md`'s worktree-disposition acceptance criterion.

## 6. Memory rules

Store: durable verified facts, owner decisions with date, traps with the commit they were seen at,
evidence paths. Never store: secrets, env values, DB URLs, PII, GSTINs, whole reports, whole
contracts/prompts, a self-declared GO, a validator warning as a finding. Correct memory the moment
repository evidence contradicts it (the three-repository model was superseded on 2026-09-02 and its
memory file says so).

## 7. `export` — a standalone prompt for another session or tool (chat only)

Only when the owner asks. Rendered inside **exactly one** four-backtick ` ````text ` fence, first line
`# NEXT CLAUDE CODE IMPLEMENTATION PROMPT — COPY FROM HERE`, last line
`# END OF NEXT CLAUDE CODE IMPLEMENTATION PROMPT`; escalate the outer fence if the body contains four
or more backticks. No commentary inside the block; never written to the repository, this skill,
memory or the run-state. The body is the phase contract expanded to stand alone: repository path,
lineage and branch model · single-agent mandate with the five-line declaration · verified starting
state (with "may have moved — re-verify") · frozen and open decisions · scope and exclusions · files
to read · safety preflight (primary checkout read-only, pathspec commits, the destructive gate lane,
the shared Postgres) · dirty-worktree preservation · security, tenant and money invariants · ordered
workstreams (problem · impact · target behaviour · files · requirements · invariants · edge cases ·
tests · acceptance · docs · gate) · feedback and uiux compliance if anything renders · verification
commands (real scripts from `package.json`) · registry reconciliation · post-merge worktree disposition
· completion report contract (`worker.md` §5) · begin-execution line.
