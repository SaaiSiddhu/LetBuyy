### Install flow (implemented, two entry points)
1. Direct install `POST /app-store/apps/:id/install` (`app-store.ts:1943-2126`): requires auth + `verifySiteOwnership`; validates requested scopes against the app's declared `api_scopes` via `normalizeAppInstallScopes` (`packages/app-engine/src/index.ts:1326-1342`, rejecting unsupported scopes); upserts `app_installations` on `(app_id,store_id)`; mints a 1-hour app-scoped JWT and stores only its SHA-256 hash in `app_installations.config.oauth.access_token_hash` (2013-2021, 2055-2063); plans + inserts `webhook_subscriptions` (compliance topics force-included, see §7); registers manifest extensions/functions if a manifest is supplied in the body (2041-2052); emits `app.installed` to the outbox (2080-2087) and fire-and-forget dispatches lifecycle webhooks through webhook-service (2089-2095); best-effort non-atomic `install_count` increment (2097-2111, read-then-write race acknowledged in comment).
2. OAuth-style install `POST /app-store/apps/:id/oauth/authorize` (1592-1775): same ownership/scope checks plus HTTPS-only registered `redirect_uri` validation (`normalizeAppOAuthRedirectUri`, app-engine 1348-1374), then issues a 15-minute single-use authorization code (hash stored at config.oauth.authorization_code.code_hash, 1704-1717) and returns `redirect_to` built by `buildAppOAuthRedirectUrl` (app-engine 1376-1384).

## 3. App runtime — how third-party apps execute

There are **three distinct execution models**, all verified:

### 3a. Embedded admin apps — sandboxed iframe + postMessage bridge (client-side)
- Surface declaration: `LETBUYY_APP_MANIFEST_ADMIN_TARGETS = ['admin.dashboard.widget','admin.settings.page','admin.product.action','admin.order.action']` (`packages/app-engine/src/index.ts:198-203`).
- Host policy: iframe `sandbox="allow-forms allow-popups allow-same-origin allow-scripts"`, `allow="clipboard-read; clipboard-write"`, `referrerPolicy: 'no-referrer'` (`packages/extension-host/src/index.ts:17-18,267-273`). HTTPS-only source URLs enforced at normalization (`safeHttpsUrl`, extension-host 120-130, 195-196).
- Host implementation: `apps/merchant-control-plane/src/components/apps/EmbeddedAppBridgeClient.tsx` — origin-pinned `postMessage` protocol (`letbuyy:bridge.ready/context/resize/toast/api.request/api.response`, lines 175-209); strict origin + source-window checks (176-177); resize clamped 480-1400px (35-39).
- Session: `POST /app-store/installations/:id/embed-session` (app-store.ts:1135-1232) mints a 15-minute app-scoped bearer (`bridge_token_hash` persisted, 1196-1210) and returns capabilities. Bridge capabilities are a fixed allow-set: `'api.fetch' | 'toast' | 'resize' | 'navigation.redirect'` (app-engine 1230-1236; extension-host 156-162); checkout extensions get only `'toast' | 'resize'` defaulting to `['resize']` (extension-host 164-170).
- API access from inside the iframe is proxied through `POST /app-store/bridge/fetch` (app-store.ts:1235-1331): **GET-only**, path allowlist mapped to scopes — `products→read_products`, `orders→read_orders`, `customers→read_customers`, `themes→read_themes`, `storefront→read_storefront` (`bridgeRequiredScopes`, 290-306); token verified with required scopes (1252-1256); `store_id` pinned to the token's store (1258-1265, 308-314); installation must be `active` and token hash must match the stored `bridge_token_hash`/`access_token_hash` (1285-1291 — i.e., tokens are revocable/replaceable); the proxy then re-enters the gateway with signed internal-identity headers of the installing merchant (1303-1321). The client-side host independently enforces the same GET-only path allowlist (`normalizeBridgePath`, EmbeddedAppBridgeClient.tsx:50-64).

### 3b. Checkout UI extensions and theme app blocks — sandboxed iframe / data-driven blocks (client-side)
- Checkout targets: 5 in the manifest (`checkout.contact/shipping-options/payment-options/order-summary/thank-you .render-after`, app-engine 205-211); the extension-host runtime recognizes only the first 4 (`CHECKOUT_UI_EXTENSION_TARGETS`, extension-host 19-24 — `checkout.thank-you.render-after` is declarable but has no host-side target constant). Checkout iframe sandbox omits `allow-same-origin`: `'allow-forms allow-popups allow-scripts'`, `allow="payment; clipboard-read; clipboard-write"` (extension-host 26-27).
- Public retrieval: `GET /v1/storefront/:subdomain/checkout/extensions` returns enabled `checkout.ui` registry rows for published stores (storefront.ts:2019-2050), gated by the `FEATURE_EXTENSIONS` flag (`services/api-gateway/src/index.ts:358-362,377`).
- Rendering: `CheckoutExtensionHost` (storefront-runtime) builds frames with the extension-host policy, posts a context payload (store, currency, cart_total_minor, item_count) to each frame's origin, and accepts only origin-matched resize messages clamped 96-640px (`CheckoutExtensionHost.tsx:43-119`); mounted at 4 checkout positions in `checkout-client.tsx` (lines 858, 904, 1076, 1214).
- Theme app blocks: targets `storefront.home.after-hero`, `storefront.product.after-form`, `storefront.collection.after-grid`, `storefront.footer.before` (app-engine 213-218). Server side, `loadPublicStorefrontAppBlocks` merges (a) registry rows with `surface='theme.app_block', status='enabled'` and (b) legacy `app_installations`→`marketplace_apps.app_extensions` blocks (storefront.ts:1068-1133), and the merged `app_blocks` array is attached to the public store payload and theme-preview payload (storefront.ts:2181-2218). Client side, `injectAppBlocksIntoSections`/`injectAppBlocksIntoTemplates` in `apps/storefront-runtime/src/lib/store-service.ts:220-304,657-659` injects them into theme sections (matching existing `appBlockSlot` sections by slot, else appending synthetic slot sections); `AppBlockSlot` renders either an inline content card or an HTTPS iframe (`app-block-slot.tsx:30-129`; renderer registered as `apps.app-block-slot` in `renderer-registry.tsx:340-343`). Inline app-block content is constrained to a fixed schema (heading/body/cta_label/cta_href, app-engine `AppBlockContentSchema` 57-62) — apps cannot inject arbitrary HTML/Liquid into themes; despite the manifest renderer value `liquid_app_block`, **no Liquid execution of app block entrypoints was found in the repository** (the `source.entrypoint` such as `blocks/loyalty-rewards-card.liquid` is stored in registry rows but nothing reads/renders it; rendering uses the JSON content/settings path above).

### 3c. App Functions — server-side WebAssembly (deterministic, fail-secure)
- Manifest: `runtime: 'wasm'` only; hooks limited to `cart.discount.calculate`, `checkout.shipping.rate`, `checkout.payment.customize`, `checkout.validation.run`; HTTPS `module_url` + 64-hex `sha256` mandatory; `timeout_ms` clamped 1-5 ms; `memory_limit_kb` clamped 64-1024; `deterministic: true` literal (app-engine 220-225, 253-268, 751-793).
- Runtime (`services/api-gateway/src/extensions/app-functions-runtime.ts`): fetches the module, verifies SHA-256 against the registry before compile (137-152, cache keyed by url+sha, 154-168); instantiates with an **empty import object** `WebAssembly.instantiate(module, {})` (202-205) so modules cannot import host capabilities; JSON-in/JSON-out ABI via exported `memory/alloc/run/result_len[/dealloc]` with a 64 KB output cap (170-194); per-phase timeouts (115-126). Registrations loaded per-store per-hook only when `status='enabled'`, `runtime='wasm'`, HTTPS URL, valid sha (226-251). Output normalized to a closed operation union: `apply_discount_code | select_shipping_method | allow_payment_methods | validation_error` (app-engine 316-339, applied 376-413). Failures are converted to a checkout validation error — fail-secure, not fail-open (`evaluateCheckoutAppFunctions`, 344-382: "An enabled checkout Function failed securely…"). Execution metrics `app_function.execution.count/duration_ms/failed_securely` recorded best-effort (253-299).
- Invocation point: public checkout order creation `POST /v1/storefront/:subdomain/orders` runs the hook chain `checkout.validation.run → checkout.payment.customize → checkout.shipping.rate → cart.discount.calculate` before order creation, only when `FEATURE_EXTENSIONS` is on (storefront.ts:2285-2333; hook order constant runtime file 22-27). Validation errors abort the order with `CHECKOUT_FUNCTION_VALIDATION` (2319-2329).
- **Memory limit not enforced at runtime:** `memory_limit_kb` is stored and clamped but `executeWasmJsonFunction` passes no memory constraints to `WebAssembly.instantiate` (app-functions-runtime.ts:196-224) — only timeout and output-length limits are live. Also note the documented 1-5 ms timeout applies to module fetch, instantiate, and execution separately via `withTimeout`, and `Promise.race` cannot pre-empt a synchronous Wasm call already on the stack (213-217) — the timeout is best-effort for CPU-bound loops.

### Extension/function lifecycle registry (per-store)
- Install-time registration: a manifest in the install body is normalized (`normalizeLetbuyyAppManifest`, app-engine 795-857; strict schema version literal `2026-06-05.ws13`, line 190) and planned into per-store rows (`planAppExtensionRegistryInstall`, 944-1014); persistence revokes all prior rows for the installation then upserts on `(installation_id, extension_handle|function_handle)` (`registerAppExtensionRegistry`, app-store.ts:534-644).

## 5. OAuth — flows, token issuance, scopes; identity-platform's role

- **Identity-platform has no app-OAuth role** (grep over `apps/identity-platform`: 0 matches). The app platform is its own authorization server inside api-gateway, signing with `INTERNAL_API_SECRET || AUTH_SECRET` (`appPlatformTokenSecret`, app-store.ts:109-114).
- Grant types: only `authorization_code` is recognized (`appOAuthGrantType`, app-store.ts:121-123). **No refresh token grant exists** (grep `refresh_token` in app-store.ts: 0 matches). No PKCE parameters are read anywhere in the token route (1778-1863) — confidential-client style with `client_id` + exact `redirect_uri` match only; **no client_secret is checked** at `/oauth/token` (the route validates `code`, `client_id`, `redirect_uri` 1785-1800, plus stored code-hash + single-use redemption 1820-1830 — possession of the code is the credential).
- Token format: HS256 JWT, issuer/audience constants, payload `{appId, installationId, storeId, installedBy, scopes, jti, iat, exp}` (`createAppScopedAccessToken`, `packages/auth-core/src/index.ts:972-997`); TTL 1 hour default (`LETBUYY_APP_ACCESS_TOKEN_TTL_SECONDS = 60*60`, auth-core 306), authorization-code TTL 15 minutes (auth-core 309). Verification checks alg, signature, expiry, and required scopes (`verifyAppScopedAccessToken`, auth-core 999-1054).
- Three issuance paths: (1) `/apps/:id/oauth/authorize` → code → `/oauth/token` (1-hour token; code single-use via stored hash + `redeemed_at`, 1820-1851); (2) direct install returns a 1-hour token inline (2113-2120); (3) `/oauth/token-exchange` swaps an authenticated merchant session for a 15-minute embedded token, with scope narrowing against `scopes_granted` (1866-1940). Embed-session mints its own 15-minute bridge token (1181-1192). In every path only the SHA-256 hash is persisted.
- **Critical scope-of-use fact:** the app access token is honored **only** at `POST /app-store/bridge/fetch` — `verifyAppScopedAccessToken` has exactly one production call site (app-store.ts:1253; repo-wide grep). The general gateway `authMiddleware` accepts only Supabase tokens or signed internal-SSO headers (`services/api-gateway/src/middleware/auth.ts:164-247`) and never app JWTs. Therefore a third-party app server holding an OAuth access token **cannot call `/v1/products`, `/v1/orders`, etc. directly**; its entire API surface is the GET-only, 5-prefix bridge proxy. There is no server-to-server write API for apps. ("Server-to-server REST/GraphQL Admin API for apps: not found in repository.")

- `POST /app-store/installations/:id/charges` (app-store.ts:1334-1477): merchant-initiated (ownership-checked), modes `recurring|usage`, INR-only (`CreateAppBillingChargeSchema`, billing-core 80-90), idempotent by `(site_id, idempotency_key)` (1388-1407); `planAppBillingCharge` computes the India payout split — default 80/20 revenue share (`DEFAULT_APP_REVENUE_SHARE_BPS=8000`), 18% partner GST, payout rails `razorpay_route|razorpayx|upi|manual` (billing-core 261-268, 567-641); inserts `app_billing_charges` with `status='pending_merchant_approval'` and an `approval_url`, and emits `app.charge.created`.
- `POST /app-store/charges/:id/approve` (1480-1590): ownership-checked, flips to `active`, and — load-bearing — fabricates the provider reference when none is supplied: `` `rzp_route_test_${chargeId…}` `` (line 1541) with `provider_mode` defaulting `'test'` (billing-core 583). **No call to Razorpay Route / RazorpayX / any PSP exists in the app-charge path** (the only provider SDK calls in webhook-service/payments routes are for storefront orders and platform subscriptions). Partner dashboard surfaces charges/payout entries and aggregates (app-store.ts:2435-2540).
- Usage metering: `MerchantApprovedUsageChargeSchema` exists (billing-core 39-45) and is wired into Razorpay subscription add-ons for **platform plans** (701-712); the ops-only `POST /v1/operations` usage-record endpoint exists (`RecordUsageSchema` used at operations.ts:700). **No app-facing usage-reporting endpoint** (an app cannot post usage records itself; not found in repository).

### Stripe wiring
- Stripe is live for **merchant/storefront payments and platform subscriptions**: `services/webhook-service/src/index.ts:1043-1247` verifies `stripe-signature` (timestamp-tolerant via `@letbuyy/infrastructure/stripe-adapter`, 276-280) and handles `checkout.session.completed`, `customer.subscription.updated/deleted`, `invoice.payment_succeeded/failed`, `payment_intent.succeeded`, with idempotency through `payment_webhook_events` upsert on `(provider, provider_event_id)` (54-92). App charges never touch Stripe; the app-charge provider enum is India rails only (billing-core 77).

## 7. Webhooks — topics, delivery, signatures, retries; what actually publishes

### Two webhook planes exist
**Inbound (payment providers → platform)** — `services/webhook-service/src/index.ts`: `/razorpay` (HMAC-SHA256 over raw body, timing-safe compare, 857-1036), `/stripe` (1043-1247), `/paypal` (provider verification API w/ webhook id, 1253-1385), `/cashfree` (base64 HMAC over timestamp+body, 1390-1499). All write `payment_webhook_events` first (dedupe), mark processed/failed/ignored, update orders/inventory/subscriptions, and emit domain events into `outbox_events` (`emitPaymentDomainEvent`, 308-345 — tolerant of the table being missing).

**Outbound (platform → app/partner endpoints)** — signed by webhook-service:
- Signature: `X-LetBuyy-Hmac-SHA256: v1=<hex hmac>` over `"${X-LetBuyy-Timestamp}.${rawBody}"`, plus legacy `X-LetBuyy-Signature`, `X-LetBuyy-Event-ID/Event-Type/Request-ID/Trace-ID` headers; HTTPS-only targets; 2000-char response preview recorded (`app-lifecycle-dispatch.ts:53-125`). A symmetric verifier `verifyLetBuyyWebhookHmac` is exported for receivers/tests (57-64).
- Immediate lifecycle path: gateway → service-binding `POST https://webhook-service/app-lifecycle/dispatch` guarded by `X-LetBuyy-Internal-Secret` (webhook-service 742-774; gateway caller `dispatchAppLifecycleThroughWebhookService`, app-store.ts:421-446, `.catch(() => undefined)` best-effort). Used synchronously on install/uninstall for subscriptions matching the event type (448-469).
- Durable path: domain event → `outbox_events` (`EventExecutionAdapter.emitDomainEvent`, app-store callers at 348/377; storefront order events at storefront.ts:557-619; products/orders/payments/stores/themes routes per grep) → cron `scheduled()` in api-gateway (every 5 min dev/staging, every 1 min in the third env block — `services/api-gateway/wrangler.toml:20,101,203`; handler `runScheduledDispatch`, index.ts:471-607) → `OutboxExecutionAdapter.dispatchBatch` claims via RPC `claim_outbox_events` (120 s lock), fans out per-site to active HTTPS `webhook_subscriptions` whose `event_types` match (wildcard `*` supported via `eventMatchesSubscription`), upserting `webhook_deliveries` on `(subscription_id,event_id)` (outbox-execution.adapter.ts:108-239) → cron also calls webhook-service `POST /webhook-deliveries/dispatch`, which claims via RPC `claim_webhook_deliveries`, sends, and completes/fails via RPCs with exponential backoff `min(120·2^attempts, 3600)` s, attempts capped by row `max_attempts` (webhook-service 776-851, backoff 246-249). Manual ops triggers exist at `/v1/operations/outbox/dispatch` and `/v1/operations/webhook-deliveries/dispatch` (operations.ts:385-419).
- Subscription creation: (a) merchant/ops API `POST /v1/operations/webhook-subscriptions` (HTTPS + ≥32-char `signing_secret`, `CreateWebhookSubscriptionSchema`, event-core 35-44) — but that route is ops-gated, so merchants cannot self-serve it; (b) automatically at app install via `planAppWebhookSubscriptions` (app-engine 1420-1447) from the app's `app_webhooks` rows plus an optional install-body webhook; every subscription's `event_types` force-includes the three **mandatory compliance topics** `customers/data_request`, `customers/redact`, `shop/redact` (`MANDATORY_COMPLIANCE_WEBHOOK_TOPICS`, app-engine 150-156). **No producer of those three compliance events exists anywhere in the repository** (grep `customers/redact`: app-engine constant, planner, docs, and tests only) — receivers subscribe to topics that are never published, and they are not in `DOMAIN_EVENT_TYPES`.
- Canonical topics that *can* publish (event-core 74-98, all with `webhook-service` as consumer): `store.created`, `product.created/updated/deleted`, `order.created/paid/fulfilled/cancelled/refunded`, `app.installed/uninstalled/submitted/approved/rejected`, `app.charge.created/activated`, `theme.submitted/approved/rejected/installed`, `payout.ledger_entry.created/released/failed`. Verified emitters: order.created/order.paid (storefront.ts:557-619), product events (products.ts:150 area), order admin events (orders.ts:177), app lifecycle + charges (app-store.ts), app/theme review decisions (operations.ts:245-298), theme events (themes.ts 119/752/841), store.created (stores.ts:36 / onboarding.ts:30), payout ledger (queue-workers). `payout.released`/`payout.failed`: contract only, no emitter found.
- Note an envelope/payload mismatch risk recorded as fact: `emitPaymentDomainEvent` in webhook-service writes event types like `payment.captured`, `payment.failed`, `refund.created`, `payment.subscription.activated` into `outbox_events` (index.ts:308-345, 440-452 etc.) that are **not** in `DOMAIN_EVENT_TYPES`; the outbox fanout itself does not validate against the contract (outbox-execution.adapter builds the envelope via `buildDomainEventEnvelope` from `@letbuyy/orchestration` without `validateDomainEventEnvelope`), so these flow to subscriptions matching `*`.

## 8. Permissions / scopes — definitions vs enforcement

- **No canonical scope registry.** Scopes are free-text strings stored per app in `marketplace_apps.api_scopes text[] DEFAULT '{}'` (baseline.sql:9716). The only scope vocabulary with enforcement semantics is the 5-entry bridge map (`read_products/read_orders/read_customers/read_themes/read_storefront`, app-store.ts:290-306). Other scope strings appearing in code are display/fixture-level: example manifest uses `write_discounts` (app-engine 1156), partner collaborator codes claim `['read_products','write_themes','read_orders','app_collaboration']` (app-store.ts:2513,2570) — none of these have an enforcement point; the collaborator `request_code` is a formatted string with an `expires_at` that is **never persisted or verified anywhere** (`partnerRequestCode`, 166-168; no redemption route found — "collaborator code redemption: not found in repository").
- Enforcement points that exist: (1) install-time — requested scopes must ⊆ app-declared `api_scopes` (`normalizeAppInstallScopes`, app-engine 1326-1342, called at install/authorize/token-exchange); (2) token verification — `requiredScopes ⊆ token.scopes` (auth-core 1042-1046); (3) bridge fetch — path→scope map + token check + installation-active + token-hash match (app-store.ts:1242-1291). Extension registry rows and bridge contexts carry `scopes` arrays (extension-host 47,69) but the iframe hosts do not gate anything on them client-side (informational only).
- Gaps (factual): write scopes are impossible to exercise (bridge is GET-only); manifest extension `scopes` (app-engine 248) are persisted in registry rows but never checked at render or fetch beyond what the token already carries; no scope is checked at theme app-block render or Wasm Function execution (functions act on checkout regardless of any scope). Conversely, the enforced surface (5 read scopes) is consistent: every enforced scope is also declarable.
- Other relevant guards: RBAC role categories `store|organization|partner|ops` (auth-core 46) with `requireRoleCategory('partner')` falling back to an approved `app_developers` row (rbac.ts:55-64,103-141) gating `GET /app-store/partners/dashboard` and `POST /app-store/partners/collaborator-code`; ops routes double-gated (operations.ts:58). `middleware/permission.ts` exists for store-member permissions but is not used by app-store routes (no import in app-store.ts).

## 10. Current limitations (factual, with evidence)

1. **App API surface is read-only and proxy-only.** App tokens work solely at `bridge/fetch` (single call site, app-store.ts:1253); GET-only with a 5-prefix allowlist (276-306). No write capability, no server-to-server API, no GraphQL access for apps.
2. **No token refresh / long-lived credentials.** 1-hour access tokens, no refresh grant (grep), no partner API keys (developer-portal self-documents "SKIP - NEEDS BACKEND", reference.ts:278-287, 311-319). An app's offline access dies within an hour of install unless the merchant re-authorizes.
3. **App billing collects no money.** Approval flow fabricates `rzp_route_test_*` references (app-store.ts:1541), payout ledger rows are `pending` with `payout_provider_mode: 'test'` (queue-consumer 657-664), and no payout release/PSP call exists.
4. **Mandatory compliance webhook topics are never emitted** (`customers/data_request`, `customers/redact`, `shop/redact` — subscription planner only, app-engine 150-156; no producer repo-wide).
5. **Developer tooling absent**: no CLI/SDK package (`@letbuyy/cli`/`create-letbuyy`: grep 0 hits outside docs; developer-portal reference.ts:268-276 confirms), no manifest upload UI, no way for developers to set `api_scopes`/`oauth_redirect_uris`/`app_webhooks` via product surfaces.
6. **Wasm memory limit declared but not enforced**; timeout best-effort against synchronous CPU loops (app-functions-runtime.ts:196-224, 115-126).
7. **`web_component` renderer and `checkout.thank-you` target are declarable but unimplemented** (extension-host 16-24; both hosts render iframes only); `admin.product.action`/`admin.order.action` lack contextual mounts; `liquid_app_block` entrypoints stored but never rendered as Liquid.
8. **Operational coupling of webhook latency to a cron** (1-5 min cadence, wrangler.toml:20,101,203) plus a best-effort synchronous fast path that swallows errors (app-store.ts:445).
9. **No app-level rate limiting or per-app quotas** distinct from the global query-cost limiter (index.ts:344-348; billing-core `api_requests_monthly` limits exist per merchant plan, 293-405, but no per-app enforcement found).
10. **Single-tenant install identity**: installs are keyed to `installed_by` (the installing merchant user); `GET /installations` and uninstall filter by `installed_by = customUser.id` (app-store.ts:899, 2158), so a co-owner/staff member of the same store cannot list or uninstall another user's installation through these routes.
11. **App review submissions auto-publish** (`status: 'published'` on insert, app-store.ts:841) with denormalized rating recomputation in-request (852-868) — no moderation queue for app *reviews* (apps themselves are moderated; reviews are not).
12. **Uncontracted payment events flow through the partner webhook fanout** (webhook-service `payment.captured` etc. vs `DOMAIN_EVENT_TYPES`, §7 last bullet).
