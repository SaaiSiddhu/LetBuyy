# LetBuyy — Local Development

> Local dev is a **convenience layer**. Staging and production remain the only
> *supported* runtime targets (`config/env/README.md`). All generated env files
> are untracked; nothing here changes deployment behaviour.

One command boots the apps on fixed `9000+` ports:

```bash
pnpm install     # once, or after dependency changes
pnpm dev         # 9 Next apps + Storybook + the API gateway (the default)
pnpm dev:all     # everything, including all 4 Cloudflare Workers
```

> `pnpm dev` starts the API gateway, which every page that reads data needs, and
> leaves the other three Workers (mobile-bff, webhook-service, queue-workers) out.
> Start those with `pnpm dev:all`, or `pnpm dev:services` in a second terminal.

default `9229` debugger clash). The map lives in `scripts/dev/ports.mjs` — edit
there and everything else follows.

## Commands

| Command | What it runs |
| ------- | ------------ |
| `pnpm dev` | 9 Next apps + Storybook + the API gateway |
| `pnpm dev:all` | Everything, including the 4 Cloudflare Workers |
| `pnpm dev:apps` | Just the 9 Next apps |
| `pnpm dev:services` | Just the Cloudflare Workers |
| `pnpm dev:storybook` | Just Storybook (9009) |
| `pnpm dev:setup` | Regenerate local env files (`--force`) |
| `pnpm --filter @letbuyy/customer-web dev` | A single app (fastest) |

`pnpm dev` first runs `scripts/dev/setup-local-env.mjs` (creates env files if
missing — it never overwrites your edits) then `turbo run dev --concurrency=25`.

## Performance — why the first run is slow

The first `pnpm dev` is the slow one, and it's a **one-time cold start**:

- All Next apps compile their first route **at the same time**, so they compete
  for CPU — a single route can take 30–60s when 9 apps boot together. Turbopack
  then writes a filesystem cache (`.next/cache`), so the next boot and every
  repeat visit are far faster.
- Each Cloudflare Worker runs `tsc --noEmit` on startup (wrangler's `[build]`),
  which is why they're not in the default `pnpm dev`.
- SSR pages that call the API while the backend is down add latency
  (`ECONNREFUSED` / retries). Run `pnpm dev:all` only when you need live data.

### Go faster / use less CPU

- **Run only what you're working on** — the single biggest win:
  `pnpm --filter @letbuyy/customer-web dev` (one app), or `pnpm dev:apps` /
  `pnpm dev:storybook`.
- `pnpm dev` (apps + Storybook) is already much lighter than `pnpm dev:all`.
- Turbopack compiles **on demand** — open one app tab at a time; routes you
  don't visit cost nothing. No GPU is used by any dev server.
- Later runs reuse the Turbopack cache, so they start far quicker than the first.

## Environment model

- Next apps load `apps/<app>/.env.local`; Workers load `services/<svc>/.dev.vars`.
  Both are **git-ignored** and generated by `scripts/dev/setup-local-env.mjs`
  from the committed key sets in `config/env/templates/*` (so they stay in sync
  with governance — only the *values* are localhost/dev-safe).
- Cross-app links resolve to the `9000+` ports; all runtimes share one local
  `INTERNAL_API_SECRET` so internal calls line up; Cloudflare Turnstile uses the
  official always-pass test keys; dev auth bypass is on.
- To customise, edit the generated files directly (they won't be regenerated
  unless you pass `--force`).

## Known limitations

- **No backing data by default.** The apps boot and render, but pages that fetch
  live data need the API gateway *plus* a database. The storefront in particular
  calls the gateway on every request, which in turn needs Postgres/Supabase, so
  storefront pages stay thin until you point `SUPABASE_URL` /
  `STAGING_DB_CONNECTION_STRING` at a real local stack (see
  `scripts/utilities/local-stack-up.mjs`).
- **First run installs native deps** (`esbuild`, `workerd`, `sharp`) — give
  `pnpm install` a minute.

## Troubleshooting

- **Port already in use** → something else holds a `90xx` port; stop it or change
  the value in `scripts/dev/ports.mjs` then `node scripts/dev/apply-dev-scripts.mjs`.
- **`frozen-lockfile` error on install** → run `pnpm install` (the repo pins
  `frozen-lockfile=true`; this setup adds **no new dependencies**, so the lockfile
  is unchanged).
- **Re-sync after pulling new env keys** → `pnpm dev:setup`.
