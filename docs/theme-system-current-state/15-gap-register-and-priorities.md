## 1. Method

### 1.1 Severity

| Level | Definition as used in this register |
|:--:|---|
| **P0** | **Exploitable, data-corrupting, or blocks the canonical journey.** An external or cross-tenant actor can reach it; or it writes/leaves incorrect persisted state; or a shopper/merchant cannot complete a first-class path (browse → cart → checkout → pay → account) at all. |
| **P1** | **Breaks a governance invariant or a shipped promise.** A Constitution article, an `AGENTS.md` rule, or a validator-enforced invariant is violated; or a feature the UI/docs advertise does not function. Not directly exploitable, not silently corrupting. |
| **P2** | **Hygiene / quality.** Dead code, duplicated authority, missing tests, stale counts, ergonomics. Real, but no invariant and no journey depends on it today. |

Severity is inherited from the discovery record, not re-graded, with one documented exception noted
in §6 (`SHOP-05`).

### 1.2 High-stakes

Per the operating rule set, a row is **high-stakes** when it touches any of: **money · auth · RLS ·
GST · sanitizer · public contract · a production migration.** The column names the trigger(s)
rather than repeating "yes", so a reader can see *why* a row is gated.

> The High-stakes column applies **the rule**, not each agent's per-gap boolean. Where the two
> disagree the rule wins, which widens the set — e.g. `TEN-09` was flagged `highStakes=false` by its
> agent but rewrites four RLS policies, so it reads `RLS · migration` here.

### 1.3 Authorization status

| Status | Meaning |
|---|---|
| **AUTHORIZED-THIS-ENGAGEMENT** | Named in the user's authorization: tenant-isolation P0s only. **5 rows.** |
| **ARB-GATED** | Touches money, auth, RLS, GST, the sanitizer, public storefront resolution, or a schema/migration of record. Requires ARB per [01-governance-and-invariants.md](01-governance-and-invariants.md) §5. Document only. |
| **SAFE-BUT-DEFERRED** | Additive, locally verifiable, no invariant surface — but outside this engagement's authorization. Document only. |

| `LIF-05` (repair/constrain) → `LIF-03` → `LIF-04` | Reconcile the data, then make the install transactional, **then** add the unique index. Adding the index first turns a partial install into a hard mid-sequence error; adding it last leaves a window where the invariant is unenforced. |

### 8.1 Theme-lifecycle P0s — ARB-GATED

| ID | Risk if left open |
|---|---|
| `LIF-02` | A merchant loading the theme editor silently deactivates every other theme instance for their store — a read that changes tenant state. |
| `LIF-01` | An unauthenticated internet caller writes the theme registry, marking packages `active` and versions `published` where anon can then read them. |
| `LIF-03` | A failure anywhere in the install tail leaves the store with the previous theme demoted and the new one active with no instance and no release — i.e. no resolvable theme. |
| `LIF-04` | Nothing in the database prevents multiple or zero active `store_themes` rows; the invariant lives only in one application `UPDATE`. |
| `LIF-05` | Three stores of "which theme is active" (`sites.theme_id`, `store_themes.is_active`, `theme_instances.instance_status`, plus `template_config.themeId`) can disagree with no constraint to stop them, and the storefront then silently renders from a stale `template_config`. |

### 8.2 Shopper-auth P0s — ARB-GATED

| ID | Risk if left open |
|---|---|
| `SHOP-02` | No-JS shoppers on a Liquid store can never log in or register — the endpoint returns 403 `TURNSTILE_REQUIRED` for a widget the theme never renders. |
| `SHOP-01` | Shopper passwords are brute-forceable at internet scale with no Turnstile and no auth rate limit, and a success discloses the customer's full order history. |
| `SHOP-05` † | Two incompatible HS256 token shapes share the cookie `lb_customer_session`, with a 30-minute and a 7-day TTL; a dual-accept verifier means the longer TTL silently wins wherever it is issued. |

### 8.3 Checkout / payment / GST P0s — ARB-GATED

| ID | Risk if left open |
|---|---|
| `CART-02` | An unauthenticated caller creates real orders — including COD — from an arbitrary item list, with no cart, no session and no signature, capped only at 20 requests per 5 minutes per IP. The built ART-14 signed handoff sits unused beside it. |
| `PAY-03` | Inventory is decremented before payment and never released on failure — a free denial-of-inventory primitive against any merchant's stock. |
| `PAY-01` | Every order in an India-first platform is written with zero GST. |
| `PAY-02` | No GST invoice is ever issued for any order, on a platform whose immutable-invoice machinery is fully built. |
| `PAY-04` | COD orders never post an origination ledger entry, so the account remittance later debits was never credited — the canonical ledger does not balance for COD (`PAY-R2`). |

† Graded P1 by the discovery record, P0 by the engagement brief — see §3.6.
