# 11 — Backend Consolidation: The Canonical Model Map

**This document proposes. It does not decide.** Every row is `D0_DEPENDENT` — D-0 (which backend is canonical: the Supabase/Cloudflare `services/api-gateway` architecture, Firebase, or some hybrid) remains open. Nothing here merges a domain model, rewrites the ledger, repoints a runtime, or activates a route. It records, per domain, what exists in each of the three systems today and a proposed (not decided) canonical shape, so a future D-0 decision has a real map to act on rather than starting from zero.

**Method and honesty note.** Firebase-side entries are derived from `services/compatibility/firebase_bridge/src/*` file names and, where read, their content this session. Supabase/System-C entries are derived from this repository's `CLAUDE.md` domain-model summary and prior phases' evidence documents (`00`–`09`). Agrimore-side entries are derived from `services/compatibility/agrimore_bridge/*/src/*` file/route names, **not** a full line-by-line schema read. Where evidence is thin, the cell says **UNVERIFIED** rather than being filled with an invented detail — consistent with this whole engagement's practice.

## What this document proves and does not prove

**Proves:** every domain the brief named "at minimum" has a row; every row states what is known, flags what is `D0_DEPENDENT`, and separately flags the two rows (Ledger, Fees/commissions) where the constitutional rule is fixed **regardless** of D-0's eventual outcome, and the two rows (Media, Payments) where a real, working Agrimore/Firebase implementation exists that must **never** be activated without a separate, explicit constitutional/ARB gate beyond D-0 alone.

**Does not prove:** the accuracy of any UNVERIFIED cell — those are explicitly unread this session, not silently assumed empty. Does not prove any proposed canonical model is correct or complete; does not decide D-0; does not authorize activating, merging, or deleting anything named here.
