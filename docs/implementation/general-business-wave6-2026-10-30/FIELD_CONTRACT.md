# General, Business, and KYC field contract

**Scope:** India beta, canonical `sites` profile and related KYC, order, invoice, and payment facts. This is a source-backed implementation contract for Wave 0, not deployment or provider approval. See [PLAN.md](./PLAN.md) and [READINESS.md](./READINESS.md) for the exit gates.

## Authority and access

- `sites` is the only mutable store profile. Merchant General, Business, web SEO, and Flutter use the owned `GET/PATCH /v1/stores/:id` contract. A profile PATCH must carry the last read `sites.version`; a stale version returns 409. `subdomain` and `site_type` are not editable from these settings.
- The store PATCH is constrained to the owned site and validated by `UpdateStoreSchema`. The nested **write** shapes for `business_profile` and `invoice_address` reject unknown keys. This prevents those fields from becoming an alternate store for full PAN or bank-account numbers; the official KYC reference field accepts only final characters. It does not make arbitrary free-text fields a safe place for secrets.
- `sites.legal_name`, `sites.gstin`, and `sites.gst_state_code` are the sole mutable legal/GST authority. Merchant web and Flutter read these columns even when they are null and never fall back to historical nested copies. Store PATCH rejects those three keys inside `business_profile`; both clients omit them when saving independent profile fields. Historical nested keys may remain on untouched rows until a separately verified, zero-loss data cutover; they cannot resurrect a cleared value in the supported clients.
- The public `GET /v1/storefront/:subdomain` mapper removes `business_profile` and private `site_settings`. It derives only explicitly opted-in email, phone, and HTTP(S) website as `public_contact`. Public name, tagline, SEO title/description, and allowlisted appearance fields reach the buyer renderer. A private contact value with opt-in off stays private.
- `merchant_kyc_documents` and its private R2 object keys are separate from `sites`. Merchant upload uses `POST /v1/kyc/documents/upload`; status reads use `GET /v1/kyc?store_id=…` and return a redacted projection. Merchant database roles have no direct base-table read or write after migrations 414–415. Console evidence download requires stepped-up access, reason, a clean scan, and audit logging.
- Live provider refresh waits for a current private upload and a trusted `clean` malware verdict. Pending or rejected scans return the existing redacted status without invoking a provider or recording a provider check. A clean scan permits review but does not itself verify identity or unlock settlement. A missing or unknown live provider is `unconfigured` and yields a provider-unavailable state; only an explicit `manual` selection enters the manual-review path.
- KYC reference input retains at most four alphanumeric characters across the web form, Flutter dialog, Gateway upload validator, and database constraint (paired migration 417). The migration refuses existing overlong values for a reviewed privacy cleanup instead of silently truncating them. Upload success says the security scan is pending; provider review has not begun.
- The canonical `sites.gstin` determines whether a GST certificate is required in KYC. A GST-registered store cannot retain an overall verified state when that certificate is missing or rejected. Unregistered stores treat it as optional; its individual document status remains visible. The requirement is recomputed on every owned KYC read/upload/refresh, so an edited GSTIN changes the required-document projection without rewriting prior evidence.
- The Gateway's `required_documents` list includes optional identity proof as well as GST certificate. Merchant web and Flutter use this single list and show each item's required/optional status; the web no longer appends identity proof from a separate local rule.
- The owned KYC overview exposes `private_upload_available` from the actual private bucket binding. When unbound, it keeps saved status readable, returns an upload-unavailable next action, and both Merchant clients disable upload controls until a fresh status read recovers. The upload endpoint independently returns 503 when the binding is absent. This signal covers storage availability only; it does not certify scanner or provider readiness.
- KYC refresh requires a caller-held idempotency key and a site-scoped durable receipt tied to the current document ID, upload key, and file digest. The route checks current ownership and evidence before a receipt replay; the outer generic HTTP cache must not replay an old status after evidence replacement. Web and Flutter retain a retry key after an uncertain failure. A successful replay returns the current redacted status without another provider call. These local receipts do not prove a provider charged exactly once after a process failure between the provider call and database write; a live adapter must use the provider's own idempotency contract.
- An order captures supplier, tax, merchant name, and notification facts when it is created. A GST invoice gets a unique number under the site counter lock and is immutable. Later General or Business edits apply to future orders only. Merchant order and invoice readback use `GET /v1/orders/:id` and `GET /v1/tax/invoice/:orderId`.

## Current field map

“Current” means mutable profile state. “Snapshot” means an order or invoice fact frozen at the transaction. No row below grants permission to use a KYC upload as live payout approval.

| Field or group | Canonical storage and API shape | Writer / allowed reader | Sensitivity and lifecycle |
|---|---|---|---|
| Store ID, handle, site type | `sites.id`, `subdomain`, `site_type`; owned store read, public routing by verified host | Store creation/onboarding; merchant and public resolver | Identity/routing. Settings display only; migration needed to change site type. |
| Display name, tagline | `sites.name`, `tagline`; `PATCH /v1/stores/:id`, public storefront projection | Merchant owner; buyer/editor/read-only public projection | Public. Current value can change; order and notification snapshots retain the name captured at creation. |
| Description | `sites.description`; owned PATCH/read | Merchant owner; only published public projections that explicitly use it | Potentially public marketing text. Keep KYC/PII out of free text. |
| Contact email, phone, website | `sites.business_profile.email/phone/website`; owned PATCH/read | Merchant owner; buyer only through `public_contact` when `public_contact_enabled === true` | Private by default. Clearing a field removes its JSONB key. Website must be HTTP(S). |
| Public contact switch | `sites.business_profile.public_contact_enabled`; owned PATCH/read | Merchant owner; public mapper uses it as a projection gate | Defaults off. Disabling removes current contact from public reads; prior delivered messages are historical records. |
| Store address | `sites.invoice_address.line1/line2/city/state/state_code/zip/country/phone`; owned PATCH/read | Merchant owner; order/invoice snapshot consumers receive only transaction facts | Legal/tax address, not a public contact card. Country is `IN`; PIN is six digits. Future invoices use current facts, issued invoices remain frozen. |
| Currency, locale, time zone | `sites.currency/locale/timezone`; owned PATCH/read | Merchant owner; buyer may receive relevant display locale/currency | India beta restricts currency to INR and time zone to Asia/Kolkata. Orders retain their own currency and timestamps. |
| Default SEO | API `seo_title/seo_description` map to `sites.meta_title/meta_description`; owned PATCH/read | Merchant owner; editor preview, published buyer page, metadata | Public after publication. Page/product overrides may supersede defaults. |
| Order reference | `orders.order_number` from canonical order generation; General shows `ORD-YYYYMMDD-sequence` | Order creation only; merchant and relevant buyer | Transaction identifier. Not an editable site prefix or a promise to reserve the next number. |
| Legal name, GSTIN, GST state | `sites.legal_name/gstin/gst_state_code`; owned PATCH/read | Merchant owner; tax/order/invoice process, not public store profile | Sensitive business/tax facts. GSTIN prefix must match selected state. Registered orders capture supplier facts; unregistered orders do not collect GST. |
| Trade name, entity type, PAN final four | `sites.business_profile.trade_name/entity_type/pan_last4`; owned PATCH/read | Merchant owner and authorized internal flow; not buyer | Private identity references. The profile write shape rejects unknown full-identifier keys. These values alone cannot establish KYC approval. |
| Invoice prefix and next number | `sites.invoice_prefix/invoice_number_next`; prefix editable, counter allocated atomically by invoice issuance | Merchant owner can change prefix; invoice allocator alone advances counter | Business shows a format example, not a reservation. Existing `gst_invoices.invoice_number` and supplier/tax/total facts do not change after profile edits. |
| KYC document type and final reference | `merchant_kyc_documents.document_type/document_number_last4`; private upload and redacted status API | Owning merchant submits; Gateway/provider and scoped Console review; no buyer | Private. Upload receipt is not verification. Replacement resets approval and scan state. |
| KYC file and scanner status | Dedicated `KYC_PRIVATE_BUCKET`; `merchant_kyc_documents.metadata.private_object_key/sha256/malware_scan_status` | Gateway stores; trusted scanner must write verdict; stepped-up Console may download clean evidence | Highly sensitive. Object keys/digests never enter merchant or buyer responses. Bucket provisioning, scanner, data location, retention, and deletion policy are **not yet complete**. |
| KYC provider decision | `merchant_kyc_documents.status/provider/provider_mode/provider_reference/verified_at` and `metadata.provider_verified`; redacted `GET /v1/kyc` | Contracted provider adapter and Gateway; merchant reads status only | `verified` requires current private evidence, clean scan, live approved provider reference, and explicit approval. No current live provider adapter can approve; sandbox cannot unlock payouts. |
| Merchant payment connection | Versioned `payment_credentials`, exact site/provider/mode/key and encrypted secret; payment setup API | Merchant owner through audited settings; Gateway/PSP integration | Secret material never appears in public readback. A KYC approval does not replace Razorpay's own merchant account and bank approval. |
| Payout statement and bank destination | Canonical provider payout/statement records; actual destination remains provider-owned | Provider plus audited finance/merchant readback once contracted | A commission summary is not a settlement statement. Live PA ingest remains closed until the exact site-bound account and current verified bank are persisted and checked. |

## Retention and unresolved production controls

The repository currently preserves immutable issued invoice facts and order/notification snapshots, but this contract does **not** assign a legal retention period. The private KYC bucket has no production scanner, lifecycle deletion, or approved data-location policy. Those choices require the selected provider's agreement, security/privacy review, and an explicit retention/deletion implementation before real documents are accepted. The current Cashfree Secure ID account is not provisioned, and no provider result contract or signed callback is connected. The live payout path must remain closed.
