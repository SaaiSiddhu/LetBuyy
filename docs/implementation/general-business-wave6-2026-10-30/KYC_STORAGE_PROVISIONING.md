## India-region candidate and decisions

AWS S3 in Mumbai (`ap-south-1`) with same-region GuardDuty Malware Protection for S3 is the first candidate to evaluate. [S3 region placement](https://docs.aws.amazon.com/en_in/AmazonS3/latest/userguide/Welcome.html), the [Mumbai endpoint](https://docs.aws.amazon.com/general/latest/gr/s3.html), [SigV4 browser POST policy](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-HTTPPOSTConstructPolicy.html), [presigned upload replay/overwrite behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), [version-specific HeadObject checksums](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html), and [GuardDuty's versioned scan events](https://docs.aws.amazon.com/guardduty/latest/ug/monitor-with-eventbridge-s3-malware-protection.html) describe the relevant platform capabilities. No AWS account, contract, cost, region configuration, or successful upload has been verified here. Security and privacy owners must approve the complete data flow, including any processing outside India, before provider setup or real files.

## Implementation and acceptance sequence

1. Confirm the AWS account and written India-only data-flow decision. Keep all real upload flags off while account, bucket, scanner, and retention work proceeds.
2. Implement one deployed India-region private-storage adapter in the canonical Gateway/Console path. Keep the R2-shaped object store confined to owned tests; do not create a second live KYC storage system.
3. Use India-only ingress for real bytes. Bind the upload session to the authenticated site, document type, file digest/size and expiry; verify and pin the completed S3 object **version** before creating or updating the canonical evidence row. Preserve idempotency and orphan/replacement cleanup. A returned browser POST or S3 `201` by itself is not an accepted KYC document.
4. Ingest authenticated scanner results for the exact current object version. Block provider review and reviewer download until a trusted clean verdict exists; handle duplicate, late, forged, and outage events without upgrading status.
5. Run synthetic staging journeys for web/mobile upload, tenant denial, file and scan failures, reviewer download, orphan/replacement cleanup, outage/retry, and retention. Record account, region, deployed SHA, bucket policy, scan event and database readback. Only then seek security/privacy approval to accept real staging documents.
6. Contract and integrate the KYC and payment providers, then pass all eight Wave 6 journeys and finance/security/owner live-canary gates. A file upload or clean malware scan is never proof of identity or bank ownership.
