# Private KYC storage and scanning gate

**Status: real-document intake closed.** On 2026-11-01 the owner required both KYC document storage and malware scanning to remain in India. No India-region storage account, scanner, retention policy, or deployed upload path has been accepted. This is a provisioning and verification plan, not approval to collect PAN, bank, address, or identity files.

## Current implementation boundary

- The existing `KYC_PRIVATE_BUCKET` is a Cloudflare R2-shaped **owned-test fixture only**. The Gateway rejects its use for deployed upload, cleanup, and Console download even if `KYC_UPLOAD_ENABLED=true`; the binding validator rejects `KYC_PRIVATE_BUCKET` in default, staging, and production Wrangler manifests. Public `R2_BUCKET` continues to serve ordinary media and must never hold KYC bytes.
- Owned tests cover file type/size checks, tenant ownership, idempotent receipt reservation, private object metadata, redacted reads, replacement/orphan cleanup, and reviewer access with step-up, reason, scan verdict, and audit. They do not prove India residency, a trusted scan, production retention, or provider verification.
- When the owned-test upload path is open, the Merchant Next proxy and Cloudflare Gateway receive file bytes before writing the fixture. Both now check canonical admission before parsing a closed upload, but an India-region bucket alone would not establish that the entire real-document path meets the owner's India-only requirement. The approved implementation must document and test upload transit, temporary storage, logs, scanner, event delivery, download, backups, and deletion.
- A read-only Wrangler check on 2026-11-01 reached an account that returned `10042` for R2 bucket listing and `10007` for the named Gateway Workers. The repository does not pin an account ID. That observation does not establish the deployed LetBuyy account's resources and is no longer a KYC storage selection criterion.
- Candidate adapter functions in `packages/infrastructure/storage-adapter/kyc-india-s3-post.ts` and `kyc-india-s3-head.ts` construct a short-lived SigV4 browser POST for **only** `ap-south-1` and reject a completed object unless an authenticated version-specific S3 HEAD reports the exact expected version, size, type, SHA-256 checksum, SSE-S3, and no replication status. Focused policy/signature and metadata-verifier tests passed 4/4; infrastructure typecheck passed. They have no Gateway route, signed HEAD transport, AWS account, bucket, or scanner binding and **do not open intake**. A browser POST `201` alone does not prove that a specific object version is safe to review.
- Paired migration `421_kyc_india_upload_intent` expands the **existing** private-object receipt with site/document-bound checksum, size, type, last-four, idempotency, expiry, storage provider, HEAD verification time, and object version. The `app_tenant` role can insert/read only its own pending India intent; it cannot mark a receipt completed. A KYC evidence row claiming India S3 storage must reference a matching HEAD-verified receipt, and the replacement trigger carries the old provider/version into cleanup. Owned Postgres migration/rollback/RLS test `6d94b304087e` passed 1/1; the existing R2 upload regression `927acb7335d4` passed 5/5 against the final migration. No Gateway endpoint writes or completes these India receipts yet, so real intake remains closed.

## India-region candidate and decisions

AWS S3 in Mumbai (`ap-south-1`) with same-region GuardDuty Malware Protection for S3 is the first candidate to evaluate. [S3 region placement](https://docs.aws.amazon.com/en_in/AmazonS3/latest/userguide/Welcome.html), the [Mumbai endpoint](https://docs.aws.amazon.com/general/latest/gr/s3.html), [SigV4 browser POST policy](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-HTTPPOSTConstructPolicy.html), [presigned upload replay/overwrite behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), [version-specific HeadObject checksums](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html), and [GuardDuty's versioned scan events](https://docs.aws.amazon.com/guardduty/latest/ug/monitor-with-eventbridge-s3-malware-protection.html) describe the relevant platform capabilities. No AWS account, contract, cost, region configuration, or successful upload has been verified here. Security and privacy owners must approve the complete data flow, including any processing outside India, before provider setup or real files.

## Implementation and acceptance sequence

1. Confirm the AWS account and written India-only data-flow decision. Keep all real upload flags off while account, bucket, scanner, and retention work proceeds.
2. Implement one deployed India-region private-storage adapter in the canonical Gateway/Console path. Keep the R2-shaped object store confined to owned tests; do not create a second live KYC storage system.
3. Use India-only ingress for real bytes. Bind the upload session to the authenticated site, document type, file digest/size and expiry; verify and pin the completed S3 object **version** before creating or updating the canonical evidence row. Preserve idempotency and orphan/replacement cleanup. A returned browser POST or S3 `201` by itself is not an accepted KYC document.
4. Ingest authenticated scanner results for the exact current object version. Block provider review and reviewer download until a trusted clean verdict exists; handle duplicate, late, forged, and outage events without upgrading status.
5. Run synthetic staging journeys for web/mobile upload, tenant denial, file and scan failures, reviewer download, orphan/replacement cleanup, outage/retry, and retention. Record account, region, deployed SHA, bucket policy, scan event and database readback. Only then seek security/privacy approval to accept real staging documents.
6. Contract and integrate the KYC and payment providers, then pass all eight Wave 6 journeys and finance/security/owner live-canary gates. A file upload or clean malware scan is never proof of identity or bank ownership.

**Safe pause:** keep real upload admission disabled while preserving the approved India-region storage, scanning, review, and cleanup access for any already accepted evidence. Do not delete current documents or roll back evidence migrations without a reviewed recovery and retention plan.
