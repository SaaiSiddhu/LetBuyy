# General and Business Wave 6 — implementation and acceptance ledger

**Status: IN PROGRESS / NO GO for production.** Source work is in `codex/general-business-kyc`, rebased onto `origin/develop` `a2f05798f` after the shipping/GST merge. This file records evidence, not a release approval.

## Decisions

- India-only store profile: INR, Indian store address/PIN, Asia/Kolkata. GSTIN state must match the selected GST state. Order references come from the order trigger (`ORD-YYYYMMDD-sequence`); GST invoice numbers come from the invoice prefix and six-digit sequence. The editable next invoice counter is removed from mobile.
- General, Business, web storefront SEO preferences, and mobile store/SEO save the canonical `sites` row with `version` compare-and-swap. A stale web/mobile save returns HTTP 409. Cleared nested contact and business fields are removed from the JSONB object. Public contact is an explicit opt-in, off by default; the public API derives only the selected email, phone, and website from the private profile.
- Merchant-owned Razorpay payments remain the canonical money route; LetBuyy does not custody or disburse funds. Razorpay Partner onboarding is the preferred source of Razorpay payout eligibility *if LetBuyy is accepted into the Partner program*. For independent India PAN/GST/bank checks, **Cashfree Secure ID is the first commercial candidate** because it publishes self-serve access, ₹100 trial credits, and ₹3 per bank-account verification; PAN/GST prices and contractual use still need confirmation. IDfy's prepaid credits and Signzy's India API sandbox are comparison candidates. Sumsub's India corporate registry check is in its highest fee tier and its published Basic minimum is for individual verification, not a complete KYB quote, so it is not the default for this India-only beta. No vendor is selected, contracted, or integrated yet.
- Live Razorpay Route settlement ingest and payout release are held closed. Global Route credentials, account ID, and approval reference do not prove a merchant-specific linked account or its current verified bank. The sandbox path remains available. Reopening live PA split requires a persisted site-bound provider account and bank approval, change/revocation handling, exact statement binding, reconciliation, and finance/security/human sign-off.
- KYC evidence uploads use a distinct `KYC_PRIVATE_BUCKET`, never the public `R2_BUCKET`. The web and mobile API paths accept bounded PDF/JPEG/PNG (mobile photo flow JPEG/PNG), sniff file signatures, store private object metadata, hide object keys from API responses, and reset resubmissions to pending. The route claims a canonical site-scoped `idempotency_keys` receipt from the file digest before the object write; a completed key cannot replace a newer document. Missing private bucket or receipt table fails closed with 503. Legacy URL submission is rejected. Sandbox references and uploads cannot become live verified. A live verified state requires an approved automated provider reference and explicit `provider_verified` evidence; no current live provider adapter can produce it.
- KYC base rows contain private R2 object keys and file digests. Paired migration 415 removes the authenticated owner SELECT policy, so merchants read only the tenant-checked, redacted Gateway projection; the server role retains base-row access. Its DOWN refuses to restore direct reads after any KYC evidence exists. New uploads start with a pending malware scan. Console review lists only redacted status; downloading bytes requires a current stepped-up Console session, `merchant:pii`, a recorded reason, a clean scan verdict, and a successful audit write. No scanner integration can currently produce that verdict in production.
- The merchant KYC projection now exposes only a safe scan stage and provider-unavailable boolean. Web and mobile show security scan pending/failed, sandbox received, and provider outage distinctly from provider review. Refresh allowlists provider flags, clears stale outage state, and cannot overwrite the private object pointer, digest, or scanner verdict. These states are local/synthetic until the actual scanner and provider callbacks are connected.

## Provider research used for the current candidate order

- [Cashfree Secure ID verification suite](https://www.cashfree.com/kyc-verification) lists PAN, GST, bank, and KYB checks; its [verification pricing FAQ](https://www.cashfree.com/payment-gateway-charges/) describes one account and ₹100 trial credits; its [bank verification page](https://www.cashfree.com/bank-account-verification/) publishes ₹3 per check for pay-as-you-go. The ₹3 figure is for bank verification, not a quote for the complete KYB journey.
- [Cashfree PAN verification documentation](https://www.cashfree.com/PAN-verification/) says the PAN check requires the complete PAN. The present last-four field and private document upload are evidence collection only; a real provider flow needs a governed full-PAN/OCR or hosted verification handoff, data handling terms, and an exact result contract before automated approval can ship.
- [Razorpay Onboarding APIs](https://razorpay.com/partners/onboarding-apis/) require Partner enrollment and a sales/integration process; a third-party KYB check cannot be substituted for Razorpay's merchant approval.
- [HyperVerge India modules](https://docs.internal.hyperverge.co/modules-and-apis/india/modules/) cover GST/PAN-related KYB and bank checks; [IDfy's FAQ](https://eve-docs.idfy.com/pages/faq/general.html) describes prepaid credits. Neither published a comparable complete KYB price in the reviewed material.
- [Sumsub's registry tiers](https://docs.sumsub.com/docs/global-corporate-registry-check-tiers) put India in Tier 4, the highest service-fee category. A plan quote for business verification would still be required.
