## Personalization contract

The exact metadata namespace is `personalization`. It contains version 1, a positive facts revision, 1–4 methods, a bounded grapheme range (1–80), explicit `latin-name` or `unicode-letters` character policy, and 1–8 named styles/placements per method. Unknown fields, duplicate IDs, invalid ranges and malformed historical facts are rejected. Missing facts yield null and honest missing-information copy. Private metadata never enters this leaf's public result.

The buyer draft contains only `method_id`, `style_id`, `placement_id`, `text`. No price, provider, upload, proof workflow or accepted-status assertion is accepted. Text retains spaces, punctuation and capitalization exactly. NFC changes return an explicit suggestion and require a separate affirmative action followed by review. Unsupported controls, bidi/zero-width characters, unsupported scripts, markup and emoji fail the declared character policy. UI locale does not imply supported engraving scripts.

The accepted representation records version, current facts revision, exact text and server-resolved IDs/labels. Fingerprint **input**, not a security digest, is deterministic JSON `[version, revision, method_id, style_id, placement_id, text]`. Asha and Kabir therefore produce different input while sharing one inventory SKU. Prices remain catalog/server authority. This first contract has no method surcharge and no variant-level personalization override.

The UI keeps invalid text visible and retains the last valid illustrative preview with an explicit note. Any edit invalidates review. The written summary echoes exact accepted text/method/style/placement. `readReviewedDraft()` rechecks current DOM fields and returns null until a valid review and canonical base eligibility both exist. The caller must use that getter at the actual cart side effect, then the server must revalidate against current catalog facts. Destroying the binding blocks purchase and removes listeners. A malformed/unenhanced required configurator fails closed.

3. Liquid projection uses `product.personalization.methodSummary: string` for section product cards and validated pre-serialized `product.personalization_json` for the PDP island. All relevant product sections use their existing `section_products` data; the scalar also survives the collection.products fallback depth. The global drop depth 4 and generic JSON sanitizer stay unchanged. Raw nested facts exceed that budget. The pre-serialized scalar is emitted once through the renderer's existing automatic escaping; an additional `|escape` double-encodes JSON. Encode `<`/`>`/`&` inside JSON as `\u003c`/`\u003e`/`\u0026` before projection so the data-attribute sanitizer does not discard the entire payload. Actual-render tests parse the final DOM attribute and prove exact equality, including hostile labels/quotes.
4. After the Threadline lease permits, the existing add-to-cart island must bind the owned helper, call `setBasePurchasable` from its canonical variant/inventory decision, require `readReviewedDraft()` before adding a required configuration, and forward the draft through the typed cart contract. No separate cart is introduced.
5. Server cart line identity must include the server-validated configuration fingerprint, in addition to product/variant/listing. Same-SKU Asha and Kabir must remain separate through quantity/edit/remove/read/hydration. Failed Kabir→Kabir-Rae must retain the failed draft and original accepted line until success. 6. Canonical checkout binding must include configuration revision/IDs/exact text (or the server-computed fingerprint) and quantities. Configuration tampering must invalidate the binding. Preserve original-attempt recovery for unknown payment outcomes.
7. Carry the accepted per-item configuration atomically into immutable order item snapshots. Expose a sanitized typed summary to the buyer and merchant. Later product edits must not rewrite fulfillment instructions. Root owns RPCs/migrations/rollback and reconciliation qualification.
8. Demo dispatch must select this synthetic catalog only for the theme preview, never seed an installation or live merchant. Root owns preview sessions/routing and marketplace/editor leases.

Minimal variant proposal: continue the existing durable UUID/option/stock variant contract. Personalization is product-level, so no name-per-SKU creation, no inventory split, and no new variant personalization namespace is required. Creation payloads use the existing title/options/stock fields and server-created IDs; editing addresses existing variant IDs and preserves omitted stock/options.
