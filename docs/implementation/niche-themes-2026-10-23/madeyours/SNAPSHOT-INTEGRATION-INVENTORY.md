## Implemented pure contract

`ProductFactSnapshotSchema` validates `{version:1,facts,personalization?}` for storage under the existing `product_snapshot.niche`. Its facts compose the nine canonical leaf schemas; no arbitrary metadata is copied. Namespace and total byte limits remain 64KiB/128KiB. Accepted personalization is mandatory when frozen capability facts require it, and must match the frozen revision and exact server-resolved labels/options/text.

`PersonalizationCartDraftSchema` extends the existing buyer draft with required positive `facts_revision` and required `review_fingerprint`. The latter is an echoed server-derived stale-review guard, not authorization or client hash authority. The client supplies method/style/placement IDs and text; client accepted flags, labels, prices, configuration hashes and extra fields fail strict parsing. The existing owned helper currently returns the simpler draft; its revision/digest-bearing getter needs subsequent integration. Revision alone is insufficient.

`prepareProductFactSnapshot(unknown)` accepts a **server-only** context: product UUID, observed positive product version, raw product metadata, whether variants exist, the selected canonical variant UUID/parent UUID/raw metadata, and the untrusted buyer draft. The caller must fetch and authorize those rows; structural validation cannot prove database existence, tenant ownership, stock or transactional freshness. The function checks variant-parent consistency, required selection, strict declared facts, current personalization revision and all text/method/style/placement rules.

It reuses `resolveToyFacts`, `resolveFurnitureFacts`, `resolveSportsMeasurements` and `mergeBooksVariantFacts`. Food quantities always come from the selected variant when variants exist; missing/null selected pack quantities stay null, with no inheritance from a differently sized parent pack. Dimensions/units replace together. Toy list/dimension clears and completeness resets remain intact. Book/stationery kind conflicts fail. A sports measurement override without required common activity/type cannot form the canonical SportsFacts and fails as a conflict, rather than inventing or dropping facts.

Success returns a cloned, deeply frozen snapshot, observed product version/IDs, `configuration_fingerprint` and `snapshot_fingerprint`. WebCrypto SHA-256 is portable to the existing Worker runtime. Configuration identity binds canonical product/variant UUIDs, capability revision, method/style/placement IDs and exact NFC text. It excludes quantity so the existing cart can merge equal configurations while separating Asha/Kabir. The snapshot digest additionally binds all frozen facts/accepted labels and observed product version, so changed fulfillment facts or version invalidate the handoff binding. Marketplace listing scope remains part of the existing cart line key, outside this helper.

`readProductFactSnapshot` validates historical snapshot data against its own frozen capability facts and never reconstructs it from today's catalog. No snapshot means unavailable historical facts. The module performs no query, mutation, price calculation, event emission or logging. Accepted text is private order/cart data; the existing anonymous fact reader/presenter does not project the snapshot or accepted representation.

Focused tests cover missing/invalid/private/accessor metadata, canonical UUID/version/variant-parent checks, stale/missing/forged draft, Unicode/NFC, exact SHA-256 oracle and distinct configurations, quantity-independent grouping keys, frozen source copies, changed snapshot/version digests, food pack non-inheritance, whole measurement units, Book kind and Toy clear semantics, strict historical readback and public-projection non-disclosure. This proves the pure contract; the small grouping-key test does not qualify the real cart merge or database concurrency.

### Mandatory revision invariant and server review digest

`validatePersonalizationRevisionTransition(previousNamespace, nextNamespace)` is the pure reference guard for the existing canonical product writer: unchanged canonical facts allow the same revision; revision decreases fail even when other content is unchanged; any change excluding revision requires a strictly higher revision. Adding/removing capabilities invalidates reviews. The next namespace must be valid or explicitly absent (`undefined`, not JSON null). Deliberate repair/clear of invalid historical facts is allowed because those facts cannot produce a valid review. Callers pass the full proposed namespace after merging the mutation; omitted metadata in a partial product edit means unchanged, not removal.

This TypeScript check is feedback, not the concurrency authority. The actual `apply_product_edit_v1` function in migration385 must repeat the invariant **after** obtaining the product row lock and the existing idempotency-receipt replay check, before writing. A rejected revision must leave the product, variants and receipt unchanged. An original accepted intent replay must still return its original receipt without applying again or being rejected against a later product version.

`personalizationReviewFingerprint({product_id,product_version,facts})` derives a SHA-256 digest from server-selected canonical identity/version/validated capabilities. The producer must expose only this opaque digest, not widen the public product version/raw metadata allowlist. `prepareProductFactSnapshot` independently recomputes it and compares the client echo as well as the revision. Thus same-revision label/style/placement changes cannot accept an older review even before writer enforcement lands. Removal/re-addition with identical facts also invalidates the old review through the advancing product version. The digest is product-level because personalization capabilities currently have no variant override; selected variant identity is separately bound in the configuration hash.

This reuses the existing product version and introduces no counter, signer, credential flow or authorization token. It is conservative: a product-version advance from another edit also requires a fresh buyer review. The canonical writer must advance the parent version for every capability removal/addition/edit; confirm every supported variant/capability mutation shares that writer/lock. A client cannot select its own server context. Current facts/options are still validated independently of every echoed digest. Tests reject revision-only payloads, forged digests, same-revision meaning changes, simulated source-version races and old reviews after removal/re-addition. Actual PostgreSQL race proof remains pending its lease.
