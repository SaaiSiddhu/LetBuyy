# F2.6 — operator identity and privileged actions

Phase 2, 2026-09-27. D04 (`DECISIONS_AND_ACCEPTANCE.md`): "Operator bootstrap, recovery, MFA and
high-risk separation of duties" — genuinely **OPEN_FOUNDER_DECISION**. This package completes real,
bounded implementation gaps within the existing scaffold (per the mandate: "Complete the existing
internal console system rather than introducing a replacement... Resolve implementation gaps within
accepted policy") and presents D04 rather than inventing bootstrap/recovery/MFA-factor/role policy.

## Fixed this phase: the operator moderation read-path break (F-ADM4-1 #5)

Full detail and evidence in the commit (`fix(gateway): F2.6 -- close operator moderation read-path
break`). Summary: `channel_listings`/`channel_listing_moderation_events` are registered tenant tables,
so the gateway's tenant guard refused every operator read even through the service-role client — a
correctly-permissioned operator (`review:decide`) could pass authentication and RBAC and then get a
500 on every attempt to approve, reject or take down a marketplace listing. No operator could complete
this workflow through the real path before this fix. Closed with two narrow, allowlisted, tested
exceptions (`getSupabaseAdminUnguarded` for the single-row bootstrap lookup,
`getSupabaseAdminForOperatorRead` — new this phase — for the permission-gated cross-site queue),
justified under D-ONE-IDENTITY's explicit delegation of "how an operator reads across tenants" to
technical design (ART-08/SEC-R9), not a fresh policy question. A previously-`todo`-marked test
(`operator-moderation-auth-chain.test.ts`, "an authorized operator approves a pending listing") now
passes for real. Negative-controlled (stash-revert-restore) to confirm the tests genuinely detect the
regression, not vacuously pass.

## What already exists and is genuinely tested (not reasserted, cited)

  (`operator-moderation-auth-chain.test.ts`, test 1: `Authorization: Bearer <PLATFORM_CONSOLE_API_TOKEN>`
  → 401 before any data lookup). This is the single most load-bearing F2.6 property and it holds.
- **Cross-realm token coercion** (a customer/buyer/app token presented as a merchant/operator
  credential, symmetric-algorithm coercion against the asymmetric verifier): `identity-redteam.test.ts`,

- **MFA hardening** (`console-mfa.ts`, SUSTAINED-E): lockout after 5 failed attempts (5-minute
  window), HOTP replay rejection (a code already accepted for this or an earlier 30s window is refused
  even if resubmitted correctly), constant-time comparison throughout. 8/8 `console-mfa.test.ts`,
  re-run fresh. The dev-bypass gate (`canUseConsoleDevMfaBypass`) requires all three of
  `NODE_ENV==='development'`, `LETBUYY_ENABLE_DEV_AUTH_BYPASS==='true'`, and
  `!isProductionConsoleRuntime()` — confirmed by reading current source, and by fixing the stale
  contract test that had stopped actually checking it (see the `test(contracts)` commit this phase).

## Genuine gaps, named precisely, not fixed (fixing them means resolving D04 first, or is out of the
## single-tier scaffold's reach entirely)

1. **No role concept inside the console at all.** `PLATFORM_CONSOLE_ALLOWED_EMAILS` is a flat
   allowlist; every allowed email gets identical access once past MFA;
   `console-auth-server.ts`'s `writeConsoleAuditLog` hardcodes `actor_type: 'super_admin'` for every
   session regardless of who it is. **The mandate's own required negative test — "restricted reviewer
   invoking privileged mutation" — cannot be constructed against the current console UI/session layer,
   because there is no restricted tier to construct it from.** This is not a test I skipped; it is a
   property the code does not yet have. (The gateway-side `employees`/`review:view` vs `review:decide`
   RBAC, by contrast, genuinely does have two tiers and IS tested — see F2.5 and the fix above — but
   that system is not wired to the console's own sign-in/session layer at all; an allowed console email
   reaches the console UI with no `review:*`-shaped scope attached to their *console* session, only
   (separately) to whatever `employees` row their *gateway* identity might independently hold.)
2. **A second symmetric-secret deviation, named precisely in F2.1**: `PLATFORM_CONSOLE_SESSION_SECRET`
   (HMAC). A leaked secret could forge a console session cookie that arrives already claiming
   `mfaVerified: true`, which `requireConsoleSession({ mfa: true })` trusts as minted rather than
   re-verifying server-side per request. Not fixed this phase (fixing it means touching the console's
   whole session model — exactly the "harden the existing scaffold as if it were permanent" pattern
   the owner's SUSTAINED-E instruction warned against extending further without the actual migration).
3. **Bootstrap and recovery remain undefined**, as they were on 2026-09-24: no document names who is
   authorized to provision the first production operator or approve an account recovery.
   `PLATFORM_CONSOLE_ALLOWED_EMAILS`/`PLATFORM_CONSOLE_TOTP_SECRETS` are both environment-provisioned,
   out-of-band, with no in-product enrollment or recovery UI at all — the safest possible default
   (nothing self-service to attack) but also not a designed bootstrap policy, just an absence.
4. **No identity-platform Admin/operator realm exists** (re-confirmed in F2.1: zero
   operator-realm-minting code anywhere in `apps/platform/identity`). The console's session and the
   gateway's `employees`-based RBAC remain two unconnected systems.

## Real browser journey — ordinary account denied console authority

`apps/internal/console` (`:9007`) was found in the same wedged state as identity-platform/api-gateway
were during the Phase 1R integration pass (same symptom: `Internal Server Error` on every request,
same long-uptime — 1 day 2h39m — same fix). Restarted the same way (`pnpm run dev` from the primary
checkout, output captured), confirmed healthy, then ran the actual journey through the real page:
navigated to `/login`, submitted a genuinely unauthorized synthetic email
(`phase2-hostile-outsider@example.invalid`, not on `PLATFORM_CONSOLE_ALLOWED_EMAILS`), and the app
redirected to `/login?error=access_denied` with the page rendering "Access denied." — a real,
browser-driven confirmation of Section 17.C's first required item ("ordinary account denied console
authority"), not a source-reading inference. A third independent occurrence of the same long-running-
dev-server wedge strengthens (does not newly prove — still not root-caused) the Phase 2 handoff item
already named in the Phase 1R integration record.
