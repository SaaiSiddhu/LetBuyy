## What does NOT exist yet (verified absent, not merely undocumented)

- **No identity-platform "operator"/"Admin" realm.** `grep`ed the entire `apps/platform/identity/src`
  tree for any operator/admin-realm session-minting function: zero matches. `AUTHORITY_MATRIX.md`
  (2026-06-08) marked this row 🔴 as a target, and SUSTAINED-I's decision package 2 (2026-09-24) found
  the same absence. **Still true today.** The console's own session (above) is a wholly separate,
  pre-identity-platform scaffold.
- **No role/permission concept inside `apps/internal/console` itself.** Its only gate is a flat email
  allowlist (`PLATFORM_CONSOLE_ALLOWED_EMAILS`) plus TOTP MFA; every allowed email gets identical
  access once past MFA (`console-auth-server.ts`'s `writeConsoleAuditLog` hardcodes
  `actor_type: 'super_admin'` for every session — there is no lesser role to record even if one
  existed). The gateway-side `employees`/`requirePermission` RBAC (a real, working, tested permission
  system) is a **completely different, unconnected mechanism** that the console's own UI does not
  surface as distinct roles to its own sign-in flow.
- **No `identity-foundation` org-model activation.** `FEATURE_ORG_MODEL`/`FEATURE_NEW_PERMISSION_ENGINE`
  confirmed still default-off (`packages/auth-core/src/feature-flags.ts`); `apps/merchant/web` still
  authenticates staff purely through `apiClient.employees.*` with zero identity-platform references
  (re-confirmed this phase, matching SUSTAINED-I's 2026-09-24 finding — **unchanged in the three days
  since**).

## The `CUSTOMER_SESSION_SECRET` deviation (C-1) — investigated, not just cited

Per the mandate's explicit instruction not to blindly replace every symmetric session with asymmetric
JWTs: this session type (`store_customers`/per-store login) is a **bounded, scoped session envelope**,
not an independent identity issuer in the sense the merchant/buyer realms are. It:

- carries no cross-realm authority claim (no `role`, no way to become a merchant or operator token —
  `identity-redteam.test.ts` pins the gateway rejecting it on merchant routes, re-confirmed present
  this phase, not re-run);
- derives its tenant scope from the **storefront host**, not from a claim inside the token itself, so
  a forged token (if the secret leaked) could not by itself select an arbitrary site — it would still
  need to be presented at that site's own host, which is the same exposure shape the buyer realm's own
  storefront session accepts by design (site named in a signed claim there, vs. resolved from host
  here — both ultimately trust the host/routing layer for which site is in play);
- is explicitly named `TRANSITIONAL` by D-ONE-IDENTITY (2026-09-24), "each with a named retirement
  gate" — the retirement gate itself is not yet defined in any document this phase found.

**Conclusion:** C-1 remains real design debt (the verification key is still the forgery key, which is
strictly worse than an asymmetric scheme if `CUSTOMER_SESSION_SECRET` ever leaks), but it is **not**
the same severity class as a rogue *issuer* minting cross-realm authority — it is a scoped, bounded
envelope whose blast radius is one storefront's login state. Collapsing it onto the sole issuer is
real, scoped Phase-2-adjacent work (migrate `apps/commerce/web`'s per-store login to a
`storefront_session`-shaped, identity-platform-issued token, matching the pattern D-8/APPID-P4b already
built for the buyer realm) — **not attempted in this pass**: it is a live-traffic-shaped migration
(every existing per-store customer session would need a compatible cutover), which the mandate's own
boundary ("preserve intended session compatibility... keep hosted cutover out of scope") places outside
a single local-only phase. Recorded here as the concrete Phase-2-handoff item it is, not silently
deferred.

## The console session's own symmetric-secret deviation — newly named precisely this phase

`PLATFORM_CONSOLE_SESSION_SECRET` (HMAC via `createLetbuyyPlatformSessionToken`) is architecturally the
**same class of deviation as C-1**, but for the operator/console realm, and it was not named with this
precision in `security.md`'s existing register (that document's "Platform operator (`admin_web`)" row
described only the gateway-perimeter half — `X-Platform-Console-Token` — not the browser-facing session
cookie layer sitting in front of it). Its blast radius if the secret leaked: forge a console UI session
(subject to the still-separate MFA gate, which the forged session would arrive already claiming
`mfaVerified: true` for — **a genuine escalation path if the secret leaks**, since the cookie payload's
`mfaVerified` boolean is trusted as-is by `requireConsoleSession({ mfa: true })` with no server-side
re-verification per request). This is a real finding, distinct from D04's bootstrap/recovery/MFA-factor
policy question — it is an implementation property of the existing scaffold, not a policy choice.
**Not fixed in this pass** (fixing it correctly means minting the `mfaVerified` claim from a source the
session token itself cannot forge, which touches the console's whole session model — exactly the kind
of "harden the existing scaffold further as if it were the permanent answer" the owner's SUSTAINED-E
instruction warned against). Named here for the Phase 2 handoff instead.

## Merchant-session revocation — resolved: database-backed, not a gap

Unlike the buyer and storefront-buyer paths, `createIdentityIssuedMerchantSessionToken` mints no epoch
claim. Traced rather than assumed: `session.ts`'s `createSession` registers each session with the
gateway (`/auth/custom/sessions/create`), and `reset-password/route.ts` calls `destroyAllUserSessions`
(`/auth/custom/sessions/destroy-all`) after a successful reset — a real, DB-backed revocation path,
architecturally different from the buyer realm's stateless JWT-epoch approach but not weaker by design.
**Not traced to completion**: which exact per-request gateway check consults that session row (so a
still-unexpired JWT for an already-destroyed session is genuinely rejected, not merely assumed to be)
was not opened this phase — the two route files above are enough to establish the mechanism exists,
not enough to certify it is wired correctly end to end. Left as a named follow-up, not reported as
verified.

## 4 October correction — merchant-session row is checked on each Gateway use

The source trace above is complete for the request path. Identity `validateSession()` calls
`GET /auth/custom/session`; Gateway verifies the Identity-issued merchant JWT and then calls
`validateMerchantSessionToken()`, which invokes `validate_and_rotate_merchant_session`. The internal
session-auth middleware invokes the same database RPC before constructing an employee auth context.
Migration 175 locks the active session row, rejects a recorded `revoked_at`, expired or idle session,
and updates activity on accepted use. Identity logout and logout-everywhere update the relevant
`sessions` rows with `revoked_at`; password reset calls the latter. Thus the normal database-backed
path does not rely on the JWT expiry alone for revocation.

The owned Foundation Wave 4 SQL regression in
`tests/executable/foundation-wave4-session-postgres.test.mjs` exercises migration 161's session
rotation, reuse detection and rollback against Postgres. This source refresh did not rerun that
separate suite and does not claim a fresh real Identity-password-reset-to-Gateway-rejection journey.
Gateway's explicit missing-local-schema development fallback remains a separate dev-only path and
must not be read as production revocation evidence. This correction supersedes only the “not traced
to completion” uncertainty above; it does not change the session design or close the broader F2.1
transition.
