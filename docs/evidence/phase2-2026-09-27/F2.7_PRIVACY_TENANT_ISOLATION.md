## Privacy workflow contracts — one confirmed absence, tied to D05, not built

Searched for a buyer-facing data-export or account-deletion path in the canonical buyer realm. What
exists (`routes/app-store/compliance-routes.ts`) is a **different thing**: outbound compliance
webhooks LetBuyy fires *to installed third-party apps* (`customers/data_request`, `customers/redact`,
`shop/redact`, a Shopify-style app-platform contract) — not an inbound, buyer-facing "export my data" /
"delete my account" capability for LetBuyy's own `buyer_accounts` realm. **None was found.** This is a
genuine, confirmed absence, not a gap I ran out of time to find.

Per the mandate's explicit instruction for exactly this situation ("Where retention/deletion policy is
unresolved: identify the affected record categories; propose options; implement safe workflow
boundaries without irreversible deletion; keep the policy-dependent portion blocked") and given D05 is
open: **not built this phase.** Building a real export/deletion feature is net-new capability, not a
gap in an existing implementation — the distinction the mandate itself draws for F2.1-F2.7 generally
("Prefer completing existing canonical implementations over introducing parallel... systems" presumes
something to complete). Affected record categories, named for the Phase 2 handoff: `buyer_accounts`
(profile fields), `buyer_addresses`, `buyer_order_links` (a link table — the underlying `orders` rows
are merchant-owned business records with their own, likely longer, accounting-driven retention
obligation, which is exactly why this needs D05 before any deletion implementation: a buyer-initiated
deletion of their own account cannot honestly promise to remove records a merchant is separately
obligated to keep).
