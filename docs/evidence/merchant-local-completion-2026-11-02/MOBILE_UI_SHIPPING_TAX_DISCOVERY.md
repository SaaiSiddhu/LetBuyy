## Actual tasks and current source gaps

- Shipping has Zones/Rates modes. Its zone form edits name/country/state/PIN lists; rate form edits zone/name/type/price/order range/ETA/active. Four rate types already exist: flat/free/price_based/weight_based. Preserve supplied country/product configuration; do not infer a different business policy from a hint string.
- The canonical rate model/input supports min/max weight grams and nullable COD eligibility, but the current rate editor does not bind these controls. **Weight update loss is a concrete source risk:** `ShippingRateInput.toJson(forUpdate:true)` emits min/max weight keys even when null, and the current edit UI constructs that input without the saved weights. A saved weighted rate edit therefore sends null criteria. Reproduce the exact dispatched payload/persisted readback before closing this; preserve serializer/backend meaning and bind the existing fields through the UI.
- The current rate edit form lets the user select another zone, while the canonical update serializer intentionally omits zone_id and the service validates the returned original relation against the selected input. An attempted move can become an unconfirmed response after other fields save. Respect the existing immutable-update contract in the UI; do not add server reparenting or another command to imitate a supported move. Reproduce this path and retain original IDs/readback.
- The existing service and typed SDK already expose shipping-profile list/create/update, exact handling_fee_minor, COD default and expected-revision updates. A full lib reference search found no normal mobile caller outside ShippingTaxService. Zone inputs also already support profile assignment and nullable COD, without current UI bindings. This is a missing reachable mobile capability, not an absent backend or authority to invent one. Trace supported web/API behavior before implementing the appropriate canonical profile task and fields.
- Taxes has a current authorized store read, configured rates and the existing tax-inclusive store setting. Its full rate editor covers name/rate/country/state/HSN/applies-to/priority/active/shipping/compound. Preserve all authoritative flags, field omission/null semantics, serializers, calculations and server validation. Default form18 is existing input copy, not a legal recommendation or evidence that a merchant owes that rate.

Rate and tax editors are complex full-page tasks, with native keyboard, full labels, preserved dirty drafts, visible validation/progress and exact current record/scope/return identity. Consequential delete remains a brief canonical confirmation. Reuse existing canonical shells/fields/choice/records/feedback; preserve store-keyed retirement and after-route controller lifetime.

Reproduce short-height/large-text loading/error/action Rows, long zone/rate/tax names, full address/range/HSN data, same-query refresh, covered/disposed callbacks, denial, unknown values, interrupted commands and current-store readback. Keep current formula/formatting bodies and API commands protected. Missing price/rate/ETA fields must not become confirmed zero/default delivery promises. Do not change tax/checkout calculations, units, GST/legal policy or durable business-operation recovery under frontend scope.
