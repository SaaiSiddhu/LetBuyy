## Methodology

Governance is text an agent must **(a) find** and **(b) obey**, with a machine that **(c) blocks** it if it doesn't. For each known drift path I asked four questions and verified each against code, not prose:

1. **Is there a rule?** — cite the rule ID + `path:line` in the 7 docs.
2. **Is the rule LIVE-discoverable?** — would an agent reading the repository *today* actually encounter it? The decisive fact: the operative `AGENTS.md` an agent reads is **still the drifted generated file**, and `CLAUDE.md` points agents at `AGENTS.md` first. AGENTS_V2 is **not promoted** (it lives only in `GOVERNANCE_REWRITE_2026_06_10/`, which nothing references).
3. **Is it machine-blocked?** — is there a validator/CI gate that *fails* the wrong action? I read the actual validator source, not the rule's `[validator-gap]` self-claim.
4. **What is the EXACT fix?** — the rule text to add/strengthen, the validator/CI gate that must back it, and whether it requires promoting AGENTS_V2 / retargeting validators.

The "evidence base" (forensic + canonicalization) is treated as *why*, not authority (per the Constitution's own P.3). I did not re-litigate any winner; I tested only whether the governance can **enforce** the winners it already chose.

## Per-path detail for the dangerous ones

### Path 5 + 11 + 9 — the topology/governance triad (the inversion)
These are the most dangerous because the machine is not neutral — it is **adversarial to the new law**. `governance-common.mjs` blesses the 9-app + CQRS estate; `runtime-manifest-validator` *requires* CQRS ownership; `repository-intelligence-validator` *requires* the drifted `AGENTS.md` text; `production-deploy.yml` ships the rejected apps; the live `AGENTS.md:356` tells agents to regenerate the drift. ### Path 3 + 10 — money (highest catastrophe-to-effort, zero machine backing)
The Constitution makes money its strongest prose (`ART-10/11/12/13`, `R-5…R-10`) and AGENTS_V2 mirrors it (`PAY-R1…R10`). Yet **there is not a single money validator**: no `commission_bps=0` ratchet (ART-12 names it as required and it does not exist), no canonical-ledger-writer gate, no never-custody/`razorpayx` ban, no mutable-balance-as-truth ban. An agent can (a) add a capture path that posts zero ledger entries, (b) default `commission_bps=300`, (c) disburse from an own-balance rail and stamp `no_custody:true`, with a fully green gate. Because the roadmap flags the money S1s as "one config flip from active loss" (FOUNDATION_ROADMAP §1), these gaps are the ones most likely to convert directly into lost merchant funds. **Fix:** author the four money validators as a Wave-1 deliverable and make them gate-lane; they do not depend on promotion (they can ship first) and are the cheapest large risk-reduction available.

### Path 1 — Liquid vs React (the gate is backwards)
`theme-governance-validator` asserts `THEME_LIQUID_RENDERING_DEFAULT_ENABLED=false` MUST be true (`:56-57`) and pins the React registry to exactly 24 sections (`:35-36`), reading `apps/storefront-runtime/src/lib/theme-engine/renderer-registry.tsx`. As a *default-off* control this is consistent with the C3 "don't flip Liquid prematurely" rule — but it provides **no** brake on growing the React fork (THEME-R2's actual concern), and an agent extending the React renderer to a 25th section is *only* stopped because the count assertion happens to fail, not because any rule about freezing React is enforced. **Fix:** re-scope the validator to a true freeze (section count must not exceed the frozen baseline; no new React section files) and keep the Liquid-default-off assertion separate.
