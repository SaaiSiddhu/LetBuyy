### What the marketplace fix batch actually changed (commits `23264816`, `07069433`, `771e835e`, `34fd95eb`, `16301b73`, `9c6c0cef`, `a5d0266f`, `31165b21`, `f31cc8b6`)

1. **Install/uninstall idempotency (H9) — landed.** `POST /apps/:id/install` and `DELETE /apps/:id/install` now read `X-Idempotency-Key`, claim through a new `IdempotencyExecutionAdapter` against the `idempotency_keys` table (scopes `app-store.install`/`app-store.uninstall`), replay completed responses, and release the key in a `finally` block on any non-success exit (`app-store.ts:1978-1994, 2158-2169, 2197-2213, 2310-2323`; adapter `services/api-gateway/src/execution/idempotency-execution.adapter.ts:35-178` — request-hash mismatch ⇒ 409, in-flight lock ⇒ 409, completed ⇒ replay). The marketplace BFF forwards the header (`apps/app-marketplace/src/app/api/apps/[id]/install/route.ts:18,27,43,45`); the shared api-client maps `options.idempotencyKey` → `X-Idempotency-Key` (`packages/typescript/api-client/src/index.ts:117,1495`). Idempotency is **opt-in** — no key, no dedupe. Side-effect of design: the **completed install response — including the plaintext app `access_token` and webhook `signing_secret` — is persisted in `idempotency_keys.response_body`** (`app-store.ts:2143-2159` stored via `complete()` at adapter line 155) and replayed verbatim on key reuse for up to 24 h (`expiresInSeconds` default, adapter line 69).
2. **Server-side webhook signing secrets (M5) — landed.** Client-supplied `webhook_secret`/`webhookSecret` is no longer read in either install path: `defaultSigningSecret = crypto.randomUUID()` unconditionally (`app-store.ts:1691` authorize, `:2061` direct install; secret stripped from the install-body webhook builder at `:327`); the BFF intentionally does not forward `webhook_secret` (`install/route.ts:26`). Caveats: app-configured `app_webhooks.secret` DB rows still override the generated secret (`planAppWebhookSubscriptions`, app-engine `:1435` — unchanged), the OAuth-authorize install never returns the secret at all (`:1770-1784`), and "show once" is undermined by the idempotency replay persistence noted above.
3. **Review requires active installation — landed.** `POST /apps/:id/reviews` now 403s unless the reviewer has an `app_installations` row with `status='active'` (optionally store-scoped); `is_verified` is hard-coded `true` for accepted reviews (`app-store.ts:820-837`). Reviews still auto-publish (`status: 'published'`, `:851`) with inline rating recomputation (`:862-878`) — no review-moderation queue (first-pass limitation #11 stands, narrowed to installed merchants).
