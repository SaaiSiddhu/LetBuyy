## 1. Architecture overview (verified)

LetBuyy's theme system is a Shopify-OS-2.0-style section/block model with **two renderer engines** declared in one shared package:

1. **JSON-contract engine** — themes are JSON configuration (`StoreTemplateConfig`: themeSettings + sections + sectionGroups + per-route `templates`); rendering of each section is performed by first-party React components compiled into `apps/storefront-runtime`.
2. **Liquid engine** — themes are portable bundles of `.liquid` layout/section/block sources validated by Zod schemas and rendered server-side with `liquidjs` (dependency declared at `packages/theme-engine/package.json:20` — `"liquidjs": "^10.27.0"`).

Both engines are defined in `packages/theme-engine/src/theme-renderer.ts`:
- `JsonContractThemeRenderer` (lines 82–102)
- `LiquidRenderer` (lines 104–211), built on `new Liquid({...})` at lines 230–251 with `dynamicPartials: false`, `strictFilters: true`, `renderLimit: 250`, `memoryLimit: 2_000_000`, plus output sanitization `sanitizeRenderedHtml` (lines 471–476: strips `<script>`, inline `on*=` handlers, `javascript:`/`data:text/html` href/src).

Theme data, drafts, releases, instances, purchases, and preview sessions are persisted as **JSONB rows in Supabase Postgres tables** — there is **no Supabase Storage / object-store usage for themes anywhere in TypeScript source** (a repo-wide grep for `storage.from(` over `**/*.{ts,tsx}` returned no matches). The only file-storage reference is the *schema-level* column `theme_assets.storage_provider DEFAULT 'r2'` (`database/supabase/migrations/000_baseline.sql:12445`) — and no application code reads or writes `theme_assets` at all (see §5).

## 5. End-to-end chain: marketplace → install → render (with evidence at each hop)

1. **Author/upload.** Partner uploads a JSON bundle file in `apps/theme-marketplace/src/components/theme-upload-panel.tsx:41–45` → marketplace BFF → gateway `POST /themes/packages/upload` (second pass themes.ts:491) → Zod validation `UploadThemePackageSchema` (theme-bundle.ts:509) → `SchemaRegistryExecutionAdapter.uploadThemePackageBundle` writes `themes` + `theme_packages` (status `draft`) + `theme_package_versions` (release_status `draft`) + both manifests; `installable = (status==='active' && release_status==='published')` is false for marketplace submissions (adapter 256–261); a `marketplace_review_records` row + `theme.submitted` domain event are created (themes.ts:103–134, :519–558). The merchant private path (`apps/merchant-control-plane/src/app/api/themes/install/route.ts:26–31`) uses `submission_mode: 'private_install'`, which skips review and publishes immediately (themes.ts:515–517).
2. **Review/approve.** Operations actor decides via gateway `POST /operations/marketplace-reviews/:id/decision`; `publishThemeReviewDecision` sets `theme_packages.status='active'`, latest version `release_status='published'`, and `themes.is_active=true` (operations.ts:183–237); emits `theme.approved` (282–297). Only then does the catalog list it (`getTheme` filters `is_active=true`, adapter:247).
3. **Browse/purchase.** `apps/theme-marketplace` lists via `GET /themes` (second pass: failures surface as `MarketplaceUnavailableError`, theme-service.ts:31–67); paid themes go through `POST /themes/:slug/purchase` (Razorpay order, themes.ts:606) + `/purchase/verify` (:785); install of premium themes is gated on a completed `theme_purchases` row (second pass adapter:820–832).
4. **Install.** Marketplace `/install` server action OR merchant themes page → gateway `POST /themes/:slug/install` → `ThemeExecutionAdapter.installTheme` (second pass: 809–920): premium-purchase gate (820–832), upserts `store_themes` (deactivating others, 834–853), resolves a renderable `template_config` (existing store config or the theme's `default_template`/`getDefaultStorefrontThemeTemplate` fallback via `resolveRenderableThemeTemplateConfig`, 859), validates it against the DB schema registry (860), ensures a `theme_instances` row (861–868), then **publishes release #N** via `publish_theme_release` RPC (supersede current → insert `theme_releases` row → update `sites.theme_id/template_config/current_theme_release_id/storefront_release_version`; `publishReleaseSnapshot` 662–689, fallback 691–807), enriches the release with `release_manifest` (incl. `liquidBundle` copy when present — `buildReleaseArtifacts` 591–638, lines 625–628), finalizes the instance (881–887), and emits `theme.installed` (892–909).
5. **Edit (second pass — now template-scoped).** Web editor (merchant-control-plane) or Flutter builder loads `GET /themes/:slug/editor?store_id=&template_key=` → `loadEditor` (adapter 1026–1110) returns store + theme + `template_config` (the **selected template's draft** if renderable, else live config; 1050–1053) + `template_key` + `templates` option list (1083–1084) + DB-resolved `schemas` (`resolveThemeRuntime`) + draft/release metadata. Autosave `PUT /themes/:slug/editor/draft` → validation → `theme_editor_drafts` upsert keyed `(store_id, theme_id, template_key)` with optimistic-version conflict check (`ConflictError` if `existingVersion > base_version`, adapter 1136–1138 — only when the client sends `base_version`; the web editor never does, the Flutter client can) + dual-write into the single (non-template-scoped) `theme_instance_drafts` row (1153–1161) + one `theme_draft_patches` snapshot row + `theme.draft.saved` domain event keyed with template_key (1169) + audit event.
6. **Preview.** `POST /themes/:slug/preview-session` requires an existing draft (adapter 1465–1467), creates a hashed token row in `theme_preview_sessions` (15-min default TTL, 1469–1501). The legacy-draft lookup at 1451–1456 is **not** template-scoped (`.maybeSingle()` over store+theme only — see §4.1 hazard note). Storefront then serves `GET /storefront/:subdomain/theme-preview?token=` which swaps the live release for a synthetic release built from the draft manifest (storefront.ts 2158–2181) — the storefront-runtime `/preview` page and `/store/[subdomain]?theme_preview_token=` both consume this (report 05 §6). **Caller today: still only the Flutter merchant app** (`theme_service.dart:123–132, 163–188` — re-verified unchanged second pass). The web editor never calls preview-session; its preview is the static in-page mock (§2.3); the merchant BFF preview-session proxy route exists with zero UI callers.
7. **Publish (second pass).** `POST /themes/:slug/publish` → `publish` (adapter 1259–1330): resolve the **selected template's** draft (1269–1278; falls back to current store config when that template has no renderable draft), optional `base_version` conflict check (1272–1274), validate, ensure instance, `publish_theme_release` RPC (new immutable release, `sites` updated, optional `status='published'` when `make_store_live` — default true per `PublishThemeSchema`, index.ts:899), finalize instance (mark instance draft `published`), delete **only that template's** legacy draft (1311 — drafts for other templates survive the publish), then gateway purges storefront cache (`purgeThemeStorefrontCache` → `bumpStorefrontCacheVersion` + `purgeStorefrontCache`, themes.ts:76–91, 431).
8. **Render.** Storefront-runtime requests `GET /storefront/:subdomain` → store row + `loadCurrentThemeRelease` → payload includes `current_theme_release` (release_config/template_snapshot/release_manifest…) + `app_blocks` → `StoreService.mapSupabaseToStore` (storefront-runtime `store-service.ts:551–710`) prefers `template_snapshot` → `release_manifest.templateConfig` → legacy `sites.template_config` (556–564), localizes, normalizes sections/templates/sectionGroups, injects app blocks into `appBlockSlot` sections, parses `liquidBundle` if present (661–662) → render plan → React sections or Liquid HTML (full pipeline in report 05).
9. **Rollback.** `POST /themes/:slug/releases/:releaseId/rollback` republishes the old snapshot as a NEW release with `rollback_of_release_id` set (second pass: adapter 1359–1440) — releases are immutable and history is preserved.

### Where the chain is broken / degraded (factual — all re-verified second pass)

- **B-1 (broken, STILL-OPEN): web editor live preview.** The complete preview infrastructure exists on both ends — gateway preview-session + theme-preview route; storefront `/preview` page + `StorefrontPreviewBridge` postMessage protocol + per-section `EditorPreviewSectionFrame`; merchant `CenterPanel` iframe component — but the active (rewritten) web editor page never mounts `CenterPanel` and never calls `/api/themes/[themeId]/preview-session` (second-pass grep: zero UI callers in merchant-control-plane; only the proxy route file itself calls `themes.previewSession` at :25). The web merchant edits against a hardcoded mock (`PREVIEW_PRODUCTS`, `editor/page.tsx:191, 1842+`). Only the Flutter app exercises the real chain.
- **B-2 (one-step publish, STILL-OPEN):** The web editor's "publish" path (`[themeId]/editor/route.ts:96–107`) is saveDraft immediately followed by `publish({make_store_live:true})` — there is no staged review/approval between draft and live for the merchant's own store (rollback exists as the recovery mechanism). `base_version` is still never sent from the web client on either call, so concurrent web sessions last-write-win at both draft and publish despite the gateway's conflict checks (adapter :1136–1138, :1272–1274) being in place for clients that do send it (Flutter does — `theme_service.dart:83, 157`).
- **B-3 (mock-vs-schema drift surface, STILL-OPEN):** the editor mock preview renders only the section types it has hand-written renderers for (announcementBar/heroBanner/categoryGrid/featuredProducts/productGrid/newsletter/trustBadges + header/footer, `editor/page.tsx:1947–1964`); every other type — including DB-registered Liquid sections — gets a generic placeholder card (:2186–2194), so a Liquid theme's editor preview cannot reflect those sections (the schemas still load and settings still save).
- **B-4 (orphaned normalized layer, STILL-OPEN):** the seven normalized theme tables in §4.2 (layouts/templates/section-definitions/block-definitions/assignments/assets/migrations) have no readers or writers; all template/section data actually lives inside JSONB manifests (`package_manifest`, `release_config`, `template_snapshot`, `working_manifest`, `draft_config`). Migration 087 did not change this.
- **B-5 (theme_reviews write path, STILL-OPEN):** the `theme_reviews` table and `ThemeReview` type exist, but no API route in the gateway or any app writes reviews — second-pass grep confirms the only code reference is the read at `themes.ts:579`. Write path: not found in repository.
- **B-6 (NEW, second pass — template-scoped drafts vs single-draft consumers):** migration 087 makes ≥2 `theme_editor_drafts` rows per (store, theme) possible, but `createPreviewSession` still looks the draft up with a non-template-scoped `.maybeSingle()` (adapter :1451–1456; `PreviewTokenSchema` carries no template_key, index.ts:903–906), and the `theme_instance_drafts` dual-write is keyed by instance only (:407–500) — the instance `working_manifest` reflects whichever template was saved most recently. Publish deletes only the published template's draft (:1311).

## 6. Theme configuration: settings schemas & presets (factual inventory)

- **Settings schema shape**: groups of typed fields (`SchemaField` types: text, textarea, richtext, color, image, select, toggle, range, number, url, radio — theme-registry.ts:12–24; identical enum in bundle contract theme-bundle.ts:82). Global settings groups in the static registry: colors (5 color fields), typography (2 font selects with fixed option lists), layout (borderRadius 0–24 step 2, enableAnimations, enableShadows), header, footer (theme-registry.ts:436–489).
- **Section schemas**: 12 static types (§2.1) + 10 runtime-only schemas declared inside the storefront app (`RUNTIME_SECTION_SCHEMAS` in `renderer-registry.tsx:66–188`: productDetail, featuredProducts, aboutSection, portfolioGrid, skillsSection, experienceTimeline, contactForm, ctaSection, servicesGrid, contentPage). DB-backed schemas from `theme_schema_manifests` override/extend these at editor time (gateway `resolveThemeRuntime`); the storefront render path consults only its compiled-in registry plus generic fallbacks (`schemaFor`, renderer-registry.tsx:190–196).
- **Presets**: per-section `presets` arrays exist in static schemas (e.g. heroBanner 3 presets, theme-registry.ts:96–100; productGrid 3; announcementBar 2; footer 2) and in the Liquid bundle contract (`ThemeLiquidPresetSchema`, theme-bundle.ts:143–148; first preset's settings become section defaults — 778). **No merchant-facing preset-picker UI was found** in merchant-control-plane (grep for preset usage in editor page shows schemas carry presets but the editor renders settings forms only via `SchemaFormRenderer`). Theme-level `color_presets`/`font_pairings` columns exist on `themes` (baseline 12923–12924) and in the `Theme` type (index.ts:971–972); no UI consuming them was found.
- **Validation enforcement points**: every draft save and publish runs `collectThemeTemplateValidationIssues` server-side (adapter `validateTemplateConfig`, second pass :242–258) — unknown section types are rejected (`…is not registered for this theme`, index.ts:478, 513), unknown setting keys rejected (380), unsafe keys/URLs rejected, 256 KB cap, ≤50 sections per legacy template / ≤80 per portable template, ≤50 blocks per section, ≤100-item arrays, ≤5,000-char strings (272–298, 401, 609, 629). Liquid sources additionally capped at 200 KB and tag-restricted (theme-bundle.ts:56, 96–119). So the claim "no section schema validation" would be false; validation exists and is database-schema-driven with static fallback.
- **Localization**: bundle `locales` map with `t:` translation prefix; storefront applies `localizeThemeTemplateConfig(resolvedTemplateConfig, storeLocale)` at read time (store-service.ts:582).

## 8. Limitations (factual, evidence-cited)

1. New JSON-contract section types require a storefront-runtime deploy; the render registry is compiled-in (`renderer-registry.tsx:198–345`). Liquid bundles avoid this (sections ship as data) but only for stores whose release carries a `liquidBundle`.
2. Web editor has no live storefront preview wiring (§5 B-1); preview-session machinery is Flutter-only in practice.
3. Theme assets have a schema (`theme_assets`, R2 provider column) but no upload, serve, or CDN code path — Liquid bundle `renderer.assets` manifests default to `{}` and nothing materializes them (theme-bundle.ts:209–215; no `theme_assets` code references).
4. Liquid bundles travel inside JSONB (`package_manifest.liquidBundle`, `release_manifest.liquidBundle`, `sites.template_config.liquidBundle`) — every storefront bootstrap response carries the full theme source; there is no separate compiled-template store or per-section cache (LiquidRenderer constructs `new Liquid({cache:false,…})` per render — theme-renderer.ts:230–232).
5. `SaveThemeDraftSchema` and `PublishThemeSchema` enforce optimistic concurrency only when the client sends `base_version` (optional — index.ts:891, :898; adapter :1136–1138, :1272–1274); the active web editor sends it on neither save (`draft/route.ts:48–53`) nor publish (`editor/route.ts:96–107`), so last-write-wins between concurrent web sessions — now per (store, theme, template). The Flutter client does send it when available (`theme_service.dart:83, 157`).
6. `theme_draft_patches` receives only whole-document snapshot patches (`compatibility_snapshot: true`, second pass adapter :471–486); the granular patch_type vocabulary (insert/move/duplicate/…) defined in the table check (baseline 12498) is unused.
7. Theme purchase currency is INR-only at the contract level (`ThemePurchaseOrderSchema currency: z.enum(['INR'])`, second pass index.ts:914–915) and provider is Razorpay-only on the gateway purchase path (themes.ts:36, 606+); `ThemePurchase.payment_provider` type also names `'stripe'` but no Stripe theme-purchase route exists — not found in repository (re-verified second pass).
8. Schema authority is still split three ways (re-verified second pass): gateway DB registry (authoritative for editor; `schema-registry-execution.adapter.ts`, 648 lines, unchanged in the remediation window), `packages/theme-engine` static registry (fallback + validation), and storefront `RUNTIME_SECTION_SCHEMAS` (render-side only; `renderer-registry.tsx:66, :191`). The storefront copy is not fed by the DB registry at render time.
9. `themes.theme_id` slug-vs-uuid duality (§4.3) means joins between `store_themes` (uuid) and `theme_releases`/`sites` (slug) require a `themes` lookup; no FK exists from `theme_releases.theme_id` to `themes`.
10. No theme CLI / dev-server / theme-check tooling exists in the repo (grep for theme-related `bin` entries found none) — confirms prior report's "NO" rows.
11. (Second pass) The template-scoped draft model is partially adopted: `theme_editor_drafts` is template-scoped, but `theme_instance_drafts`, `theme_preview_sessions`, and `PreviewTokenSchema` are not (§5 B-6); and the editor force-injects urban-kicks default sections into any theme/template missing them (`REQUIRED_URBAN_KICKS_SECTIONS`, editor/page.tsx:162–169, 570–580).
12. (Second pass) `tests/theme-engine/theme-template-editor.test.mjs` validates the feature only via regex matches against source files (migration text, schema declarations, route/adapter/page source patterns) — it executes no draft/publish behavior.
