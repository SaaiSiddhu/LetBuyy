## Platform Comparison Matrix

| Platform | Theme model | Product model | Order/payment model | Admin model | LetBuyy takeaway |
|---|---|---|---|---|---|
| Shopify | Standard theme folders, JSON templates, sections, blocks, settings data | Strong product/variant/channel semantics | Checkout/payment strongly controlled by platform | Merchant admin and theme editor are first-class | Build Urban Kicks as a versioned theme package and move edits into schema-driven publish flow |
| WooCommerce | WordPress themes and theme.json global styles | Product posts plus metadata/extensions | Store API cart/checkout with gateway extensions | WP admin and plugin ecosystem | LetBuyy needs a stable public storefront/cart API and central token contract |
| Medusa | Headless, not theme-first | Modular product, inventory, pricing, promotion modules | Workflows and modules coordinate side effects | Admin consumes backend modules | Use domain modules/workflows for LetBuyy engines |
| BigCommerce | Stencil and Page Builder concepts | Catalog plus options/variants/modifiers | Multi-gateway enterprise checkout | Merchant operations dashboard | Separate theme runtime and merchant customization data |
| Saleor | Headless storefronts and channels | GraphQL product/catalog/channel model | Apps, webhooks, checkout, payments | Dashboard and app ecosystem | Add channel/app/webhook boundaries and generated contracts |
| Adobe Commerce | Modules, layout XML, observers, queues, indexers | Deep catalog/EAV heritage | Enterprise order/payment/fulfillment complexity | Highly modular admin | Adopt event bus, indexers, queues, config scopes without copying EAV complexity |
| Commerce Layer | API-first commerce primitives | Decoupled commerce API | Payment/order APIs for headless systems | External admin clients | Keep LetBuyy API canonical and client-agnostic |
| Fabric | Composable commerce orientation | Commerce services | Extensible enterprise services | Suite-driven ops | Design LetBuyy modules so domains can scale independently |

## Competitive Lessons Converted Into LetBuyy Requirements

### Tenant and Store Context

Competitive requirement: Resolve authenticated user, active site, store slug, permissions, plan limits, and storefront public identity from one canonical middleware stack.

LetBuyy implementation stance:
- The admin app must not be a collection of independent pages. It must be a store operating console backed by worker contracts.
- Urban Kicks must expose a stable renderer contract so settings changes, product changes, navigation changes, and CMS changes are predictable.
- Flutter Builder cannot be a second source of truth. It must call the same API and parse generated models.
- Every platform-grade feature needs a migration, an API contract, a service, UI states, analytics, audit logging, and cache behavior.
