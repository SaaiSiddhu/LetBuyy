# 27 - Risk Analysis

Generated: 2026-05-22
Scope: LetBuyy Admin App, Urban Kicks storefront, Hono worker API, Supabase schema, Flutter Builder, shared packages, and production commerce infrastructure.
Status: Planning artifact. This document is source-derived from the current repository scan plus official commerce platform documentation listed below.

| Risk | Severity | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| Tenant data leak through service-role query | Critical | Medium | Cross-store data exposure | Mandatory store ownership helper and tests for every endpoint |
| Theme publish stale cache | High | High | Admin changes not visible or wrong storefront data visible | Release snapshots, cache tags, queue purger, realtime sync |
| Payment webhook replay/fake event | Critical | Medium | Fraudulent order payment state | Raw body signature verification and event id idempotency |
| Inventory oversell | High | High | Orders accepted without stock | Reservations and transactional conversion |
| Contract drift with Flutter | High | High | Mobile builder saves invalid config | Generated contracts and parity tests |
| Migration corruption | High | Medium | Broken products/orders/theme configs | Additive migrations, backfills, validation, rollback snapshots |
| Admin editor data loss | High | Medium | Merchant loses draft work | Optimistic version, autosave, conflict resolution, draft history |
| Search/cache lag | Medium | High | Storefront stale product discovery | Outbox retries, dead-letter queues, sync dashboards |
| Secrets exposure | Critical | Medium | Credential compromise | Rotate, purge, encrypt, redacted logs, secret scanning |
| Unbounded queries | Medium | High | Slow admin/storefront at scale | Pagination, indexes, precomputed aggregates, rate limits |

## Residual Risk Register
1. Admin writes are not yet consistently canonicalized through the worker. Some admin screens and route handlers still operate as app-local surfaces or use direct Supabase logic.
2. Theme publishing writes template_config but does not emit a durable event, invalidate storefront cache, notify live previews, or update a versioned theme release table.
3. Urban Kicks storefront reads published template_config with ISR revalidate 300, so admin changes are not guaranteed to appear in real time.
4. The theme schema model is split between DB theme fields, admin DEFAULT_TEMPLATE, admin SECTION_SCHEMAS, Flutter theme editor models, and Urban Kicks section JSON files.
5. Product variants are partly modeled in migrations but ProductService still treats variants as any[] JSON on products, creating Flutter/web/backend contract risk.
6. Inventory is split between scalar products.stock and inventory_levels/inventory_adjustments. OrderService decrements products.stock sequentially without a database transaction or reservation state machine.
7. Payment configuration now exists but tenant-owned gateway usage is not yet fully propagated through storefront payment creation, webhook reconciliation, refunds, and order payment attempts.
8. Order lifecycle lacks a durable outbox, event log, fulfillment tables, refund tables, shipment tracking events, and atomic stock release/reservation behavior.
9. RBAC exists as middleware scaffolding and employee tables but merchant admin role enforcement is not yet consistently applied to every admin action.
10. Web and Flutter share concepts but do not share generated contracts. Dart models parse worker responses manually and TypeScript API types are small.
11. Cache strategy is mostly implicit. Storefront uses ISR and worker has cache/rate intent, but no cache tag registry, no purge API, and no store-scoped invalidation pipeline.
12. Search indexing is not productionized. Product search, collection filters, storefront indexing, and analytics feedback loops need dedicated architecture.
13. Media storage exists in schema and routes, but a complete R2/CDN derivative pipeline, asset ownership model, and theme asset versioning are missing.
14. Production observability is incomplete. Request IDs exist as governance, but structured logs, traces, metrics, error tracking, and SLO dashboards need implementation.
15. Design system is fragmented between web Tailwind/CSS, admin components, storefront theme CSS tokens, and Flutter UI kit/theme colors.
16. The monorepo has app/package naming drift, untracked/new AGENTS for future packages, generated worker dist debt, and inconsistent ownership boundaries.

### Implementation Item: Risk governance loop

Objective: Track risks as engineering issues with owner, due date, mitigation, verification, and release gate.

Technical explanation:
- Implement this as a store-scoped domain capability, not as isolated page logic.
- The worker owns validation, authorization, tenant isolation, persistence, and event emission.
- Admin web and Flutter Builder call the same worker contract and receive the same response envelope.
- Storefront Urban Kicks consumes published snapshots and public APIs only.

Architecture impact:
- Moves business behavior out of page components and route glue into services.
- Creates an explicit admin-to-storefront synchronization path.
- Enables contract generation and parity between TypeScript and Dart clients.

Dependencies:
- Supabase migration and RLS policy updates where data shape changes are required.
- Zod schemas under backend/workers/api/src/schemas.
- Worker services under backend/workers/api/src/services.
- Admin modules under apps/web/consumer/admin/src/app/[store].
- Flutter Builder service/model updates under apps/flutter/builder/lib.

Database changes:
- Add normalized tables if the current JSON/scalar model cannot support queryability, consistency, or multi-tenant scale.
- Add store_id/site_id, created_at, updated_at, deleted_at, created_by, updated_by, version, indexes, and RLS policies.
- Add outbox_events rows for mutations that require storefront, cache, analytics, search, or webhook follow-up.

API changes:
- Add versioned /v1 endpoints in the worker.
- Require store_id in protected merchant mutations unless resolved by store-context middleware.
- Return standardized success/error envelopes and request_id.
- Add idempotency keys to mutation endpoints that create orders, payments, refunds, webhooks, imports, or publish releases.

Frontend changes:
- Replace direct local assumptions with API-backed loaders, mutations, optimistic state, error states, conflict states, and skeletons.
- Render forms from shared schema metadata when possible.
- Keep Urban Kicks preview visible for every storefront-impacting change.

Backend changes:
- Use service classes for domain logic.
- Add audit logging and domain events after successful writes.
- Sanitize errors and avoid leaking raw DB details.

Infrastructure changes:
- Route events through Cloudflare Queues consumers.
- Add cache tag invalidation, search indexing, media derivative jobs, and realtime fanout where relevant.

Security considerations:
- Validate ownership through sites/stores view plus RBAC scope.
- Never expose service-role credentials, payment secrets, webhook secrets, or internal provider responses to clients.
- Use CSRF protections for cookie-authenticated mutating routes and strict CORS for worker surfaces.

Performance considerations:
- Paginate lists, add query indexes, avoid N+1 reads, and precompute storefront release snapshots.
- Keep live preview incremental and throttle autosaves.

Scaling considerations:
- Partition hot data by store_id/site_id where possible.
- Keep search, analytics, media processing, webhook processing, and cache purge off the synchronous request path.

Risks:
- Contract drift between admin web and Flutter if generated clients are not enforced.
- Tenant data leaks if route handlers bypass store ownership checks.
- Stale storefront rendering if publish events do not purge caches.

Edge cases:
- Draft conflicts from multiple editor sessions.
- Deleted products referenced by theme sections.
- Payment provider webhook arrives before local payment attempt is stored.
- Inventory changes while checkout is open.

Testing requirements:
- Unit tests for service logic.
- Contract tests for worker schemas and client models.
- Migration tests for backfills and rollback.
- E2E tests for admin save -> publish -> Urban Kicks storefront render.

Migration strategy:
- Add new schema in parallel, dual-read legacy and new shape, backfill, dual-write, cut read path, then remove legacy reads in a later release.

Rollback strategy:
- Keep previous release snapshots, old columns, and legacy read path until metrics prove stability.

Production readiness checklist:
- Ownership and RBAC verified.
- Validation exists.
- Audit event exists.
- Outbox event exists.
- Cache invalidation exists.
- Web and Flutter parity exists.
- Urban Kicks storefront behavior verified.
