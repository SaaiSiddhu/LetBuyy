# Theme Integration Architecture

*Extracted from LETBUYY.md §13.1–§13.3 Theme System*

---

## 1. Theme Data Model

```
themes table:
  id              UUID PK
  name            TEXT
  slug            TEXT UNIQUE
  description     TEXT
  preview_images  TEXT[] (array of image URLs)
  price           DECIMAL
  site_types      TEXT[] (which site types this theme supports)
  template_data   JSONB (component layout and style config)
  category        TEXT
  status          ENUM (draft, published, archived)
  created_by      UUID FK → auth.users

theme_installations table:
  id              UUID PK
  store_id        UUID FK → sites
  theme_id        UUID FK → themes
  custom_settings JSONB (store-specific overrides)
  installed_at    TIMESTAMPTZ
  is_active       BOOLEAN
```

## 2. Theme Rendering Pipeline

```
1. Storefront request arrives (*.letbuyy.store)
2. Middleware extracts subdomain → looks up store
3. Active theme_installation fetched for store
4. Theme template_data loaded
5. Store-specific custom_settings merged over defaults
6. Site-type-specific storefront template rendered
7. ISR caches result for 60 seconds
```

## 3. Theme Component Structure

Each theme defines sections with:

| Property | Type | Description |
|----------|------|-------------|
| layout | string | `grid`, `flex`, `stack` — section layout mode |
| columns | number | Number of columns (responsive) |
| colors | object | Design token overrides for this section |
| typography | object | Font family, sizes, weights |
| spacing | object | Padding, margins, gaps |
| content_slots | array | Dynamic content binding points |
| animations | object | Entry/scroll animation presets |

## 4. Theme Installation Flow

```
Browse → Preview → Purchase/Install → Configure → Activate

1. User browses themes at themes.letbuyy.store
2. Preview shows theme with user's actual store data
3. Purchase (premium) or install (free)
4. INSERT into theme_installations
5. User customizes via admin theme editor
6. SET is_active = true to activate
7. Previous theme deactivated (is_active = false)
```

## 5. Full `template_data` JSONB Schema

```typescript
// Stored in: themes.template_data (JSONB)
interface TemplateData {
  version: string;                 // Schema version "1.0"
  design_tokens: {
    colors: {
      primary: string;             // "#6366F1"
      secondary: string;
      accent: string;
      background: string;
      surface: string;
      text: string;
      heading: string;
      muted: string;
      border: string;
      error: string;
      success: string;
    };
    typography: {
      heading_font: string;        // Google Font name
      body_font: string;
      base_size: number;           // 16
      scale_ratio: number;         // 1.25
      line_height: number;         // 1.6
    };
    spacing: {
      base: number;                // 4 (px, base unit)
      section_gap: number;         // 80 (px)
      container_max: number;       // 1200 (px)
    };
    borders: {
      radius: Record<'sm'|'md'|'lg'|'full', number>;
      width: number;
    };
    shadows: Record<'sm'|'md'|'lg', string>;
  };
  sections: Array<{
    id: string;
    type: string;                  // "hero", "product_grid", etc.
    label: string;
    enabled: boolean;
    settings: Record<string, any>; // Section-specific config
  }>;
  layouts: {
    header: { variant: string; sticky: boolean; transparent: boolean };
    footer: { variant: string; columns: number };
    product_card: { variant: string; showPrice: boolean; showRating: boolean };
    product_page: { variant: string; gallery_position: 'left'|'right'|'top' };
  };
  global: {
    dark_mode: boolean;
    rtl_support: boolean;
    max_width: number;
    favicon_url?: string;
    custom_css?: string;
  };
}
```

## 6. Theme Migration Between Versions

```
Migration Strategy:
  1. Backup: snapshot current custom_settings → theme_backups table
  2. Schema diff: compare old version template_data vs new version
  3. Auto-migrate:
     → Renamed tokens: mapping table applied (e.g., "primary" → "brand")
     → New tokens: filled with defaults from new version
     → Removed tokens: archived to custom_settings._deprecated
  4. Manual migration (for breaking changes):
     → Migration wizard shows before/after preview
     → User confirms each breaking change
     → Undo available for 7 days

Version Compatibility:
  theme_installations stores:
    installed_version: "1.2.0"
    target_version: "2.0.0"  (when update available)
    migration_status: "pending" | "completed" | "rollback"
```

## 8. Theme Asset CDN Configuration

```
Storage: Supabase Storage bucket "themes"
CDN: Supabase CDN (backed by Cloudflare)

URL pattern:
  {supabase_url}/storage/v1/object/public/themes/{theme_id}/{version}/{asset_path}

Asset types:
  - Preview images: /preview/thumbnail.webp, /preview/screenshots/*.webp
  - Fonts: /assets/fonts/*.woff2 (if custom fonts)
  - Icons: /assets/icons/*.svg

Caching:
  - Cache-Control: public, max-age=31536000, immutable (versioned assets)
  - Cache-Control: public, max-age=3600 (preview images)

Size limits:
  - Total theme package: max 50 MB
  - Individual image: max 5 MB
  - Font file: max 2 MB
```

## 9. SSR vs CSR Rendering Decisions

```
SERVER-SIDE RENDERED (SSR):
  - Theme layout (header, footer, nav)
  - Product grid, blog post list, project grid
  - SEO-critical content (meta tags, structured data)
  - Initial page paint (everything above the fold)
  - Static sections (text, images, hero)

CLIENT-SIDE RENDERED (CSR — "use client"):
  - Cart widget (dynamic, user-specific)
  - Search bar (interactive, live results)
  - Image gallery lightbox
  - Theme editor preview (iframe)
  - Animations (Framer Motion, GSAP)
  - Form submissions
  - Toast notifications
  - Dark mode toggle

INCREMENTAL STATIC REGENERATION (ISR):
  - Storefront pages: revalidate every 60 seconds
  - Product pages: revalidate on product update webhook
  - Blog posts: revalidate on publish/update
  - Portfolio projects: revalidate on save

  Implementation: Next.js generateStaticParams + revalidatePath
```
