## Findings derived directly from the two code paths above
1. COST PER REQUEST: each rate-limited request performs exactly one KV get()
   and one KV put(). This is 1 KV read + 1 KV WRITE per limited request.
2. NON-ATOMIC READ-MODIFY-WRITE: both paths read a counter, compute a new value in
   the isolate, and write it back. There is no atomic increment and no compare-and-set.
   Under concurrency, N simultaneous requests each read the same value and each write
   value+1, so the counter advances by 1 instead of N.
   => The limiter UNDER-ENFORCES precisely during a burst, which is when it matters.
   This is a SECURITY finding, not only a capacity finding.
3. EVENTUAL CONSISTENCY: Cloudflare KV is eventually consistent across PoPs, so the
   counter is per-PoP-stale. The effective limit is therefore per-PoP, multiplied by
   the number of PoPs serving the attacker/tenant. Global enforcement is not achieved.
4. PER-KEY WRITE CEILING: Cloudflare documents a hot-key write limit (see
   10_VENDOR_LIMITS_AND_COSTS.md for the fetched current value). A rate-limit key that
   is scoped per site or per route will exceed a 1-write-per-second-per-key ceiling as
   soon as that key sees more than that rate — i.e. on any busy tenant.
5. DAILY WRITE QUOTA: sustained request rate is bounded by the account's KV daily write
   allowance divided by 86400. See 07_CAPACITY_MODEL.md for the arithmetic.

## Fail-open / fail-closed behaviour
Query-cost path sets queryCostKvUnavailableUntil on error and returns
queryCostUnavailableResult(...) — i.e. it degrades on KV failure rather than throwing.
The pre-fix behaviour (per the committed comment) was FAIL CLOSED (503 on every /v1
data route). Confirm the post-fix degraded-mode posture in 08_SECURITY_PRIVACY_COMPLIANCE.md.
