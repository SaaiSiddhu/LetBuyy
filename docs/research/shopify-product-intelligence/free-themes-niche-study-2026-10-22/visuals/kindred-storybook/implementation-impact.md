## Decisive observations

1. `createFirstPartyCatalogBundle()` currently dispatches the full niche artifact only for `sense`; `summit` still receives Core plus a settings overlay. Editing a label/palette will not install Kindred’s design.
2. Summit is both the stable tenth public catalog identity and the **General/unknown-industry fallback**. `FALLBACK_EXPERIENCE_ID='summit'`, `general:'summit'`, and consumers such as store creation discard the resolver’s `source`. Changing Summit’s definition globally to gifts would change unknown/general merchants and generated section defaults.
3. Product metadata accepts arbitrary keys but validates only its known `apparel` namespace. The anonymous product serializer deliberately publishes **only valid apparel facts**; generic metadata is not a public contract. The storefront mapper and Liquid drop likewise copy `apparel` explicitly. Gift facts need all these deliberate gates; publishing arbitrary metadata would reintroduce a privacy defect.
4. The currently typed public product query has size/color/price/sort/collection fields, not occasion or recipient. Route query preservation is currently an apparel-specific allowlist. A gift finder drawn in Liquid cannot make those filters work by itself.
5. Packaging already fits the real option/variant/cart model. A blush versus kraft box should be a selected existing variant UUID and its server price; it does not require a checkout surcharge, cart message, bundle configurator or new payment authority.
6. Catalog preview currently has an explicit Threadline fixture path and otherwise falls back to Urban Kicks. Kindred must get correctly labelled gift fixtures through the selected package; reusing the shoe preview would misrepresent the installed artifact.

## Minimal proposed typed contracts

**C, not implemented.** Final field names/schema placement belong to the allocated shared-domain writer. Complete the existing `ProductMetadataSchema` rather than inventing another metadata authority. Suggested optional `metadata.gift` v1:

- `occasions`: bounded merchant-authored stable keys such as `birthday`, `thank-you`, `housewarming`, `just-because`; at most12 entries. No fabricated suitability claims.
- `recipients`: bounded preference/category keys such as `friend`, `colleague`, `family`; at most12. These describe products, not inferred personal traits or recipient profiles.
- `suitabilityNote`: plain, escaped merchant text, proposed maximum500 characters.
- `contents`: at most30 entries of `{ label, quantity, detail?, care? }`; proposed label maximum160, positive integer quantity at most100, optional detail/care at most1000. Reject malformed/duplicate semantic rows. Derive a displayed item count only when the supplied list is complete; packaging/fill does not silently become an extra included product.
- Optional `mediaRoles: { openBox?, closedBox? }` refers only to the product’s existing bounded media list. A proposed index representation must be validated against the actual media array and saved/rebound on reorder in the same product command. Invalid/missing roles yield the plain gallery with truthful captions; they must never mislabel an image. Stable media-ID support should be reused if current owner already supplies it at implementation time.
- No prices, stock, recipient PII, messages, HTML or executable content inside these facts. Missing gift facts remain absent/unknown. Do not infer contents from photos.

The full path is merchant form → validated domain command → persisted metadata → safe public serializer → typed ProductModel → deliberate `product.gift` Liquid drop → escaped card/contents rendering. An empty generic metadata object is not a successful fact readback. Retain unrelated merchant metadata while editing and never expose it anonymously.

**Discovery C:** add single `occasion?` and `recipient?` keys to the existing product query. Reuse `min_price`, `max_price`, allowlisted sort, collection, page/limit/search conventions and their existing money units. Match occasion AND recipient AND the server’s purchasable price selection, with exact returned count/pagination. Empty strings normalize away, invalid price ranges fail, clearing budget removes only its min/max values and preserves occasion/recipient/search/collection/sort while resetting page appropriately. Browser back must restore the query.

Budget results must consider the actual eligible variant: a cheaper available kraft SKU can match a lower budget, but an unavailable cheap SKU cannot falsely qualify the product. Card price/packaging copy must agree with the qualifying selection, e.g. a server-supported “From” amount and clear option choice. No client-side second price engine or invented result counts.

**Packaging A/B:** use the ordinary `Packaging` option with real values and durable variant UUIDs. The existing variant carries title/options/image/price/availability; the cart line carries product/variant/quantity. Different box variants stay different lines. The mockup SKU codes are fixture identifiers, not permission to loosen the anonymous SKU/barcode privacy boundary. Verify the existing immutable order item readback before adding any extra snapshot field. Fixed contents remain a stocked set, not a bill-of-materials inventory engine.

`services/api-gateway/src/routes/gift-cards.ts` is a financial gift-card domain, not the owner of physical ready-made gift sets. Do not route this work through stored-value, balance or redemption machinery.

**Excluded:** gift notes/messages, configurable box contents, personalization, upload/proof workflows, recipient claims/returns, delivery-date guarantees and automatic gift-recipient accounts. Cart `properties` being available does not establish an order/fulfillment message contract. No new checkout/order schema should be needed merely to choose a packaging variant.
