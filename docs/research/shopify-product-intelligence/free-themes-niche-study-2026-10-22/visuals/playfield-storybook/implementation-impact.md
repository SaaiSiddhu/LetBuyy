## 2. Minimal proposed factual contract

Extend the existing domain owner, **`@letbuyy/commerce-core`**, with a bounded Zod toy namespace under existing product metadata. Reuse `ProductMetadataSchema`; do not add another product DTO or metadata validator in an app. `@letbuyy/shared-types` remains the cross-runtime product contract. `ProductModel`, SDK transport and Liquid projection must receive the same validated domain facts intentionally.

Proposed names are a concrete integration request, not implemented exports:

| Field | Minimum semantics / resilience |
|---|---|
| `schemaVersion` | Literal `1` for the bounded namespace. |
| `ageBands` | Merchant-selected array from the initial `3-5`, `6-8`, `9-12` taxonomy; nullable/absent/empty means unknown. Never infer from title, photographs or other interests. Multi-band products may explicitly list more than one. |
| `ageStatement` | Optional merchant wording, bounded plain text. Must not silently override missing structured age or become a platform suitability guarantee. |
| `interests` / `productType` | Merchant-authored allowlisted identifiers, with readable labels; initial art, building and puzzles plus the catalog's actual types. No child profile or behavioral targeting. |
| `contents` | Bounded array of `{label, quantity}` with positive integer quantities. A supplied total may be derived only from complete counted contents; no inferred piece count from an image or an incomplete list. |
| `dimensions` | Optional `{length, width, height, unit}` with finite positive values and explicit `cm`/`mm` unit. Diagram and text derive from the same values. Do not infer dimensions from generated photography. |
| `materials`, `care` | Bounded merchant plain text. Missing material/finish remains not supplied. |
| `warnings` | Bounded `{text, sourceLabel, editionLabel?}` entries. Render exact supplied wording/source; no generated certification, safety approval or health claim. |

Suggested implementation limits for owner review: at most 3 age bands, 12 interest IDs, 30 content rows, 120-character content labels, quantities 1–10,000, 20 warning rows and 2,000 characters per warning/material/care field. These are proposed payload bounds, not observed platform limits. Reject unknown nested keys, nonfinite dimensions, negative/fractional counts, invalid units and duplicate IDs. Normalize empty optional input to unknown/absent without fabricating an empty-but-verified value. Historical invalid namespaces project as unavailable; invalid new writes produce field-level errors.

The mockup's Garden/Ocean editions share product-level piece count/dimensions. Initial product-level facts therefore suffice for that fixture. If a merchant's variant changes physical contents or size, shared facts cannot be presented as variant-specific truth: require a bounded variant override contract before advertising that capability. Do not repurpose garment size/color data for toy suitability.

This is a stocked kit sold as one existing SKU. It needs no configurator, component-inventory bundle engine, cart-properties convention or new order system. The order must preserve the real selected Edition/SKU, quantity and server amounts. Existing immutable order snapshot support for any historical toy-fact display must be inspected by the shared order owner; current product facts must not be presented as a guaranteed historical contents snapshot.

## 3. Minimal query contract

Extend the existing public product/collection query with optional `age_band`, `interest`, and, only when exposed, `product_type`; reuse page/limit/search/category/price/sort/collection scope. Validation belongs in the domain package and mounted gateway path. Query identifiers are bounded/allowlisted; empty values normalize consistently. **Age AND interest** must be applied on the server before count, sort and page selection. Unknown age is excluded when an age is active; unfiltered results may include it with the explicit unknown label.

Clear-one resets the page but preserves every other active filter/search/collection; Clear all resets only the declared discovery scope. URLs, rendered chips, results and browser Back/refresh agree. Stable sorting needs an ID tie-breaker. A page beyond the last page still returns the authoritative total. No-match, loading and failed catalog reads remain distinct. Proposed empty/unknown examples must not be mixed into real merchant inventory as demo products.

Current query extension is apparel-specific: `StorefrontApparelQuerySchema`, SDK `StorefrontProductQuery`, the `apparelRouteQuery` allowlist, `ProductService`, gateway `PublicProductQueryOptions` and `browse_storefront_apparel_v1`. Toy keys currently do not pass through these layers. The **shared query owner** should extend/generalize this one canonical browsing path with optional bounded toy predicates. Do not build a parallel search service or nine per-theme discovery stacks. The exact SQL function evolution/paired migration is centrally allocated; migration 383 is reference evidence, not an edit target.
