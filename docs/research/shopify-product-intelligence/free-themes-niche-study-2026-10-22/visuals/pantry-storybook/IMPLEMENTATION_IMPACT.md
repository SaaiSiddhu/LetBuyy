## Minimal typed contracts proposed for shared-owner review

This is a bounded contract sketch, not an implemented API or a newly ratified schema. Preserve current canonical types/exports and inbound Zod validation.

**Product food facts:** a validated namespace containing optional ingredient text; allergen status (`not_supplied` or `supplied`) plus bounded merchant statement/source when supplied; optional storage, preparation and merchant nutrition text. Allergen absence must remain unknown. An empty string must not become a safety claim. No medical inference, certification generation, expiry-date invention or nutritional calculation.

**Sellable pack quantity:** explicit facts bound to the actual product/variant identity, not SKU text, title, shipping weight or a client property. Minimal initial normalized dimension is `g` or `ml` with positive bounded integer amount per sellable unit; merchant `kg`/`l` input converts exactly to those units. Keep mass and volume incomparable. More precision/other units need an explicit contract, not guessed conversion. The shared owner must choose a compatible storage shape after actual schema inspection: baseline `product_variants` contains shipping weight but no net-content field, and create-variant input has no preassigned UUID, so a metadata map keyed by not-yet-created IDs cannot silently solve creation. No migration is allocated by this document.

**Display value:** server derives value from canonical minor-unit price and normalized quantity, with one documented rounding rule. Suggested display base is 100 g or 100 ml. ₹180/250 g = ₹72/100 g; two units = ₹360 and 500 g. Hide unit value when quantity/unit is absent; keep actual sale price. Do not introduce floating money or trust a client total. Confirm whether the existing major-unit product drop requires an explicit integer-paise presentation field; do not silently reinterpret its `price` field.

**Query extension:** existing search/category/page/limit/min-price/max-price/sort plus an allowlisted normalized pack quantity/dimension filter and server-supplied available facets/counts/URLs. No dietary filter is needed for Pantry v1: no supported dietary claims are supplied. Removing pack weight retains search/category/price; pagination is stable; mixed g/ml values never sort as if equivalent. Unsupported facets remain hidden until actual queries work. The dispatcher must preserve existing apparel behavior and indexed, tenant-scoped bounded reads.

**Cart/quote/order projection:** derive pack identity and net quantity from server-resolved variant. Preserve quantity as number of sellable packs. Snapshot safe selected pack facts into the canonical order item so a later merchant product edit cannot change the historical order’s 250 g → 500 g meaning. Existing normalized order readback must expose that snapshot; both buyer owned detail and merchant fulfillment consume it. No new order table/cart store is proposed. This is a specific shared contract gap, not a claim of working current snapshot propagation.
